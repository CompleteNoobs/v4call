1B. NEW (2026-05-28) — VERIFICATION FETCH TIMEOUT + 5-MIN NEGATIVE CACHE
    CAUSES FEDERATION FLAPPING THAT WON'T SELF-HEAL FOR 5 MINUTES
================================================================================

Symptom observed in production 2026-05-28 (immediately after the
dup-FEDERATION_PEERS fix in Lesson 11):
  All three servers have FEDERATION_PEERS configured correctly.
  v4call.com logs:
    [federation] Inbound peer connection — waiting for hello
    [federation] ✗ Peer verification failed for hive-book.com:
        Cannot fetch v4call-server.json: The operation was aborted
        due to timeout
  hive-book.com + call.completenoobs.com logs (the other side):
    [federation] Outbound connected: wss://v4call.com/federation
    [federation] Disconnected from wss://v4call.com/federation — retry in 2s
    [federation] ✓ Peer verified: @v4call.com   ← this line arrives AFTER disconnect
    [federation] Connecting to wss://v4call.com/federation...
  → endless flap; pairs involving v4call.com don't stay up.

Root cause (in server.js, NOT a config bug):
  _fetchPeerVerifyFile() uses `AbortSignal.timeout(8000)` — eight
  seconds covering DNS + TCP + TLS + HTTP for the entire fetch of
  the peer's /.well-known/v4call-server.json. Slow networks, IPv6
  dead-ends, or a momentarily slow nginx on the peer all blow this
  budget.

  AND: peerVerifyCache has PEER_VERIFY_TTL_FAIL = 5 * 60 * 1000
  (5 minutes). One timeout locks the peer out as "verified=false"
  for 300 seconds. Even if the network recovers in 10 seconds,
  every reconnect during the cache window hits the cached failure
  and instantly closes.

  Combined effect: a single transient timeout cascades into a
  5-minute outage. Reconnect logic retries every 2s but each
  retry hits the cache and bounces.

Why hive-book.com sees the "✓ Peer verified" AFTER the disconnect
  log: hive-book.com's OWN verifyPeer() runs in parallel with
  v4call.com's. v4call.com's side fails fast → closes the socket.
  hive-book.com sees the close → logs Disconnected. A moment
  later hive-book.com's own verify (a separate HTTPS fetch in the
  OTHER direction) completes and logs ✓. The log line ordering
  is correct; it's just the timing of two independent
  verifications crossing.

DIFFICULTY OF DISTINGUISHING ROOT CAUSE:
  The "timeout" message in the logs doesn't tell us WHERE the
  budget was eaten — DNS, TLS handshake, HTTP round-trip. Need
  out-of-band testing to know. The diagnostic command we ran:
    docker compose exec app sh -c \
      "time wget -qO- --timeout=20 https://peer/.well-known/v4call-server.json"
  separates "node fetch is too aggressive" from "actual network
  problem" from "container DNS broken."

DIAGNOSTIC RESULT (2026-05-28, from v4call.com):
  - Container wget to hive-book.com well-known: 0.06s
  - Container wget to call.completenoobs.com well-known: 0.07s
  - Host curl to both: 0.07s each
  - DNS resolution inside container: instant, correct IPs

→ Network is FAST. DNS / TLS / routing all healthy. The 8s timeout
  budget should be more than enough for any genuine fetch. The
  Node-side fetch is somehow eating 8s+ on a 70ms round-trip.

LIKELY ROOT CAUSES (now confirmed not network-side):
  1. Event-loop pressure: heavy concurrent work (Nostr publishes
     every 30s × 4 relays, federation handshakes from 2 passive
     peers retrying every 2s, Hive scans, hivecrypt sig
     verification, SQLite calls) blocks the loop long enough for
     AbortSignal.timeout(8000) to fire before the fetch's I/O
     actually issues. v4call.com is hit hardest because it's the
     ONLY passive server (lex largest of the three) — it receives
     TWO reconnection cycles every 2s, twice the verify load of
     either of the others.
  2. 5-minute negative cache locks the FIRST transient failure
     in for 300s. During that window every reconnect hits the
     cached fail and bounces — looks like the network is broken
     but it's just stale cache.

FIXES APPLIED (v0.16.19, this session):
  A. _fetchPeerVerifyFile timeout bumped 8s → 15s. Logged with a
     comment explaining the diagnostic finding that motivated it
     (network is fast, must be loop pressure).

  B. PEER_VERIFY_TTL_FAIL split into two named constants:
     PEER_VERIFY_TTL_STRUCTURAL (5min, kept) for bad-sig / wrong-
     claim / domain-mismatch / expired / missing-pubkey style
     failures that can't change without operator action; and
     PEER_VERIFY_TTL_TRANSIENT (30s, new) for fetch timeouts,
     network errors, HTTP 5xx, and Hive-RPC hiccups. New
     `transient` flag stored alongside `result` in
     peerVerifyCache. fail() takes a second arg `transient = false`
     and every call-site now explicitly tags its category.
     Fetcher tags HTTP 5xx as transient and 4xx as structural via
     err._transient. Lookup branch in verifyPeer reads
     cached.transient and picks the right TTL.

  C. NOT applied — IPv4 forcing was a hypothesis pre-diagnostic.
     Diagnostic ruled out network as the cause, so no need.

  D. NOT applied as part of this fix — the 30s transient cache
     means cascades self-clear in 30s. An admin-flush endpoint
     would still be a nice-to-have follow-up (also closes item
     4 below) but is no longer urgent.

DEPLOY NOTES:
  - server.js changed → operators must `docker compose down &&
    docker compose build --no-cache && docker compose up -d`
    (not just down/up — code changed).
  - In-process peerVerifyCache is cleared by the restart, so the
    fix takes effect immediately on all three servers.
  - Watch logs for `[federation] ✗ Peer verification failed` —
    should now appear at most every 30s during a real transient
    failure window, not every 2s. If it reappears after 30s of
    quiet, that's a genuine repeated failure (worth investigating
    event loop pressure further).
  - Recommended deploy order: restart v4call.com FIRST (it's the
    passive node currently in the worst flap state), then the
    other two. They'll naturally reconnect within seconds.

Severity: CLOSED (fix in v0.16.19). Re-open if logs show the same
pattern after deploy.

2. NO APPLICATION-LEVEL HEARTBEAT ON WS FEDERATION SOCKETS
================================================================================

Current state:
  The server-to-server WS links rely on:
    - TCP keepalive
    - Natural traffic (presence, user-online, etc.)
    - The reconnect logic on 'close'

  There is no explicit ping/pong or "are you still there?" timer on
  the federationPeers sockets.

Contrast with Nostr side:
  Explicit heartbeats + 30-min resubscribe because public relays are
  known to be lossy.

Risk:
  A half-open connection (one side's network stack died, the other
  side's TCP socket doesn't know yet) can persist for a long time
  (minutes to hours depending on OS TCP settings) before a send
  finally fails and triggers the 'close' handler + cleanup.

For a small trusted federation this has been acceptable. For larger
or less reliable networks it becomes a source of "ghost peers that
look connected but don't deliver".

Low-cost improvement:
  Add a lightweight application ping every 30–60s on federation
  sockets (with a matching pong handler) and treat missing pong
  as a signal to close/reconnect. Would make the two layers more
  consistent.

Severity: Low for current usage. Worth doing before public
          multi-operator growth.

Severity: Very low today. Documented limitation.

4. VERIFY CACHE CAN STALE AFTER OPERATOR CONFIG CHANGE
================================================================================

1h positive TTL on peerVerifyCache.

If an operator:
  - Rotates their signing key
  - Changes escrow account
  - Changes federation_ws URL in the well-known file

...then peers that have a cached positive verification will not
pick up the change for up to an hour (unless they restart).

On the next actual message send the connection may be in a weird
state, or the next hello will fail verification with the new file.

Workaround:
  Restart the observing servers (clears in-memory cache).
  Or wait for natural expiry.

Improvement:
  Admin action to "re-verify peer X now" or flush cache for a domain.
  Easy to add later.

Severity: Low. Rare operation.

5. NO PERSISTENCE FOR ACTIVE FEDERATED CALLS ACROSS SERVER RESTART
================================================================================

This is noted in the broader backlog (not just federation):
  "Settlement state persistence (paid sessions survive server restart)"

If a server hosting a federated call restarts mid-call:
  - The temp Socket.io connections from the remote browsers die.
  - The caller-server's credit-burn timer and cap timer are in-memory.
  - The callee-server's view of the call is also lost.

Current behavior:
  The call just ends abruptly for everyone. Disbursement may or
  may not have happened depending on timing.

This is a broader paid-call robustness issue, not specific to the
federation transport, but it surfaces most visibly in cross-server
calls.

Not urgent for the current small federation.

================================================================================
6. MANUAL COORDINATION TAX WHEN ADDING A NEW PEER
================================================================================

To add a 4th server today:
  1. Operator of new server publishes Hive announce + signs well-known.
  2. nGate scans (or they wait for the 2h Hive scan on existing servers).
  3. Each existing operator must manually approve via /admin/peers/
     or the admin-peers.html UI.
  4. The new server must list the existing servers in its own
     FEDERATION_PEERS (or discover + approve them).

There is no "trust on first use with audit log" or automatic
"introduce via a mutual friend" flow.

This is acceptable for a small, high-trust group of operators who
know each other on Hive. It will become painful at larger scale.

This is more of a "future feature" than a bug (see also the
User-Added-Servers design notes for a related but different UX).

7. MIXED-VERSION ROLLOUTS RELY ON OPERATOR DISCIPLINE
================================================================================

New additive federation message types are silently ignored by
older peers (no error, no fallback).

Only v0.4 structural changes (room invites) have an explicit
protocol_version gate.

For the current three operators who coordinate releases this is
fine. In a larger federation it creates a "feature is sometimes
missing" class of support tickets.

Mitigation already in docs:
  "Plan rollouts so paired servers upgrade together."

SUMMARY OF RISK LEVELS
================================================================================

High (needs attention before wider use):
  - None currently observed in the federation layers.

Medium (closed or future scale):
  - 1. Call initiation precheck parity — CLOSED v0.16.19.
  - 1B. Verification fetch timeout + cache cascade — CLOSED v0.16.19
        (timeout bump + cache TTL category split).
  - WS socket heartbeat / liveness detection — would have caught 1B
    earlier by detecting zombie sockets. Still on the future hardening
    list but the 30s transient cache means the failure mode 1B was
    causing no longer cascades for 5 minutes.

Low (hardening / future scale):
  - Verify cache invalidation UX (operator endpoint to flush one
    domain) — was tightly coupled to 1B, now optional. With the 30s
    transient TTL most need-to-flush scenarios self-resolve.
  - Hive scan pagination (when >20 servers)
  - Paid call restart survival (broader, not fed-specific)
  - Lower-coordination peer introduction

Active production deployment status: federation is healthy after
v0.16.19 deploys (timeout bump + cache TTL split). All three pairs
expected to stay up. Logs should show ✗ verification failure at most
every 30s during genuine transient blips, not every 2s.
