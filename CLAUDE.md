## What This Is

v4call is a decentralised paid video, voice, and text communication platform built on the Hive blockchain. Users set their own rates for receiving calls and messages. Callers pay with HBD or custom Hive-Engine tokens. Unused credit is refunded automatically. The server operator earns a platform fee from each paid interaction. Multiple server operators can federate so users on different servers see, call, and message each other.

**The core idea:** I don't want strangers ringing my phone for free. If they value my time, they can pay. If not, my phone doesn't ring. Family and friends get custom rules — free calls, different hours, different rates.

## Tech Stack

- **Backend:** Node.js, Express, Socket.io, better-sqlite3, ws (federation WebSocket)
- **Frontend:** Single HTML file (`public/index.html`) — all HTML, CSS, and JS in one file. Plus four standalone operator-tool pages (rate/sign/announce/admin-peers).
- **Blockchain:** @hiveio/dhive for Hive API, hivecrypt for posting-key encryption
- **External APIs:** Hive blockchain (identity, rates, HBD payments), Hive-Engine API at `https://api.hive-engine.com/rpc/contracts` (token balances, transfers)
- **WebRTC:** Peer-to-peer audio/video via browser APIs, STUN via Google's public server
- **Federation transport:** Server-to-server WebSocket on `/federation` (separate from Socket.io)
- **Deployment:** Docker (node:20-alpine), Nginx reverse proxy, Let's Encrypt SSL
- **Databases:** Two separate SQLite files in `/app/logs/` (mounted as `./data/logs/`) + `approved-peers.json` for federation approvals

## Architecture

```
   Browser (caller)  ──────WebRTC P2P (encrypted)──────►  Browser (callee)
        │                                                       │
        │ Socket.io                                             │ Socket.io (own server,
        ▼                                                       ▼  OR cross-server temp
   Caller's server.js                            Callee's server.js  socket for federated)
        │
        ├── Hive blockchain API (identity, rates, HBD payments)
        ├── Hive-Engine API (custom token balances + transfers)
        ├── SQLite: v4call-ledger.db (payments — server writes only)
        ├── SQLite: v4call-chat.db (encrypted DMs + room messages — separate for security)
        ├── Escrow Hive account (holds HBD + tokens during calls)
        ┊
        ┊──── Federation WebSocket (/federation) ────────────►
        ▼                                                     ▼
   Federation peer servers (presence, DM relay, call invites, payment-verified, call-ended)
```

**Federation flow at a glance** (this is the most non-obvious part of the system):

1. Each server publishes a *signed* `/.well-known/v4call-server.json` proving the Hive account at the field `hive_account` controls this domain. Operators generate it via `/server-sign.html`.
2. Each server publishes a `v4call-server` tagged Hive post advertising its existence and pointing at the verify URL. Operators generate it via `/server-announce.html`.
3. Other servers periodically scan Hive for `v4call-server` posts, fetch each candidate's verify file, cryptographically verify, and present the candidate list at `/admin-peers.html`.
4. Operator approves a candidate → outgoing federation WebSocket established (one direction only — lower-domain side initiates, see "Domain tiebreaker" below).
5. On the wire, federation messages: `hello` (with verify recheck), `presence`, `user-online`/`user-offline`, `dm`, `call-invite`/`call-response`/`call-declined`/`call-cancelled`/`call-missed`, `payment-verified`, `call-ended`, `call-receipt-fed`.
6. For paid cross-server calls/DMs, the caller pays the *callee's escrow on Hive* directly. The caller's server verifies on-chain and forwards the payment notification to the callee's server. The callee's server independently re-verifies and disburses (callee-net, platform-fee) from its own escrow at call end. Refunds to the caller are cross-server Hive transfers from the callee's escrow.

## Features (What's Built and Working in v0.16)

### Core (single-server)
- **Login:** Hive Keychain (recommended, no key paste) or manual posting key
- **Encryption unlock:** Keychain users get a 🔑 panel to enter posting key for encrypted messaging (Keychain can't expose private keys)
- **Voice calls:** Green phone button, audio only, no camera permission
- **Video calls:** Blue camera button, audio + camera
- **DMs:** Purple chat bubble button, end-to-end encrypted with Hive posting keys
- **Chat storage:** Both sender and recipient copies stored as ciphertext in v4call-chat.db, configurable retention (DM_RETENTION_DAYS, ROOM_RETENTION_DAYS)
- **Unread DM alerts:** Popup on login showing count and senders, based on last_seen tracking
- **DM previews:** Last N messages per conversation loaded on login (DM_PREVIEW_COUNT, 0 = off)
- **DM history:** Full conversation loaded on demand when opening DM panel
- **Rooms:** Private, allowlist-based, ephemeral (deleted when last person leaves, including stored messages)
- **Room history:** Replayed on join — broadcasts in full, encrypted messages only if addressed to the joiner
- **Custom token payments:** Any Hive-Engine token via [TOKEN:SYMBOL] sections in rates post. Token creation on Hive-Engine costs a flat 100 BEE (≈ 65 HIVE / ~$4 USD at 2026-04-30 — exchange rate varies; the user's own CNOOBS token works as a worked example). Cheap enough to be a real wedge for creator-economy use cases. Created tokens work as payment currency, lobby anti-spam gate, room token-gate, and blocked-list bypass without any further setup. **The SWAP.* family on tribaldex.com (SWAP.BTC, SWAP.DOGE, SWAP.ETH, SWAP.LTC, and many others) also works as payment currencies out of the box — no v4call code change needed.** They're 1:1 wrapped versions of the underlying coins (counterparty risk via the wrapper service is the trade-off; see Known Gotchas). Real-world utility: callees can take payment in BTC / DOGE / ETH / etc. terms via Hive-Engine, often with lower fees than the underlying coin's native network for small amounts. **Verified working in v4call testing 2026-05-04** — added SWAP.BTC ring fee, paid call worked end-to-end. Tutorial for buying/selling SWAP.BTC: https://www.completenoobs.com/noobs/Hive_Blockchain_-How_to_buy_SWAP.BTC
- **Payment picker:** When multiple currencies qualify, caller sees all options with balances and chooses
- **Token transfers:** Uses Keychain requestCustomJson for Hive-Engine sidechain operations
- **Token verification:** Balance-check verification (not transferHistory — that API doesn't work reliably)
- **Platform fee enforcement:** Server sets minimum (DEFAULT_PLATFORM_FEE), user's rates post sets their willingness. If user's fee < server minimum → rejected with message. If user's fee >= minimum → server charges its own rate (best price for user)
- **Rate system:** V1 and V2 formats, named lists (family/friends/work/default), time windows, day-of-week, blocked users, ALLOW-IF-TOKEN bypass, per-token rate sections

### v0.16 polish (added on top of v0.15)
- **Federation protocol bumped to v0.4.** `FEDERATION_VERSION = '0.4'`. The hello envelope adds an explicit `protocol_version: '0.4'` field alongside the legacy `version` field. v0.3 peers don't read or send `protocol_version`, so the new code reads `peer.protocolVersion` (null on v0.3 peers) and gates v0.4-only features on `parseFloat(...) >= 0.4`. v0.3 peers continue to federate fully for everything they could do at v0.3 (DMs, 1:1 calls, presence, payments) — only the cross-server room invite + join paths require v0.4 on both ends.
- **Federated allowlist input.** The `al-add-input` field accepts both `@user` (local) and `@user@server.com` (federated) forms. `parseFederatedHandle()` strips a leading `@`, lower-cases, splits on `@`. If the suffix matches an approved + connected v0.4+ peer, the entry is stored canonically as `user@server.com`; if not, the admin gets a clear `allowlist-error` system message ("not approved", "not connected", "needs v0.4"). Typing your own server's domain collapses to the local path.
- **`room-invite` / `room-response` federation envelopes.** `room-invite`: `{ invite_id, from_user, to_user, room_name, source_server, payload: {} }` — empty `payload` is the v0.17 hook (Paid Expert Invites populate it with `{ connectFee, ratePerHour, currency, maxDuration, ... }` without needing a separate message type). `room-response`: `{ invite_id, response: 'accepted'|'declined', reason? }`; `reason: 'offline'` is an automatic decline emitted by the receiving server when the target isn't online. Source-server validation on incoming envelopes (`source_server.toLowerCase() === ws._domain`) prevents a peer impersonating a third party.

Outgoing entries on the source server hold `{ room, from_user, target_user, target_server, created_at }`; incoming entries on the receiving server hold `{ target_user, from_user, from_server, room, created_at }`. A 5-minute interval prunes anything older than 15 minutes (`FED_INVITE_TTL_MS`) — covers peer-disconnect-mid-flow + user-never-responded.
- **Federated invite popup with source-server badge.** When `from_server` is set on the incoming `room-invite`, the popup renders `@from <span style="color:var(--accent)">@from_server</span>` plus a "Cross-server invite from <server>" subtext. `acceptInvite()` for federated path emits `room-invite-respond { invite_id, response: 'accepted' }`, auto-leaves any current local room (design call 5(a)), opens a temp Socket.io to the host server (existing `openFederatedRoomSocket`, same as 1:1 federated calls), and runs `enterRoom(targetRoom)` against it. Decline is silent on the inviter side (matches local-invite behaviour, design call 3).

- **No federation protocol bump.** The bypass exploited the existing federation `dm` envelope; removing the client+server emit path stops the bypass at the source. - **Lobby anti-spam gate scope tightened naturally.** Gate now only runs on `lobby-chat` (the only public lobby channel left). Correct scope — gate exists for spam, not for paid-DM enforcement, which has its own rate-check path.
- **Migration / chat history note:** old encrypted-lobby messages were already stored in `v4call-chat.db` as DMs (with `textPaid: 0`) by `chatStoreDm` in the old handler. They show up in users' DM history as past unpaid DMs. No migration needed — they stay where they are.
- **Why three rolls in close sequence:** the bypass happens on the *sender's* server (it's the one that generates the federation envelope). A v0.16.5 server stops generating bypass envelopes; a still-on-v0.16 server keeps doing so. Recipients on v0.16.5 servers still receive bypass DMs from un-upgraded peers (because they look like normal free DMs from the recipient server's perspective). To fully close the bypass across the federation, **all servers** need v0.16.5. Recommended rollout: ship to one server, smoke-test, then ship to the others within an hour. The architectural recipient-side enforcement fix (planned v0.16.6) is what fully closes the class — v0.16.5 is the immediate-bypass-path-gone fix.

- **Federation `dm` handler — recipient-side rate enforcement.** After re-verifying the on-chain payment landed in our escrow, we now ALSO call `computePaymentOptions(recipRates, from, 'text', now)` and validate that the caller isn't on the recipient's block-list, the recipient's platform fee meets our server minimum, and `paid >= option.flat` for the option matching the currency the caller actually paid in. On any failure: send `dm-failed` envelope back AND auto-refund the caller from our escrow via `sendFromEscrow(from, paid, refundMemo, cur, msgId)`. The refund pattern mirrors call-end refunds; mostly reuses existing helpers.
- **Federation `payment-verified` handler — ring fee validation + `ratePerHour` override.** For `paymentType: 'ring'`, before creating `activePayments[callId]`, we re-fetch our recipient's rates and validate (same multi-currency checks as DM: blocked, feeRejected, `amount >= option.ring` for the matching currency). Critical change: `p.ratePerHour` is now set from OUR computed `option.rate` (NOT `msg.ratePerHour` from the caller's server) — pulled from the option matching the actual paid currency. `msg.ratePerHour` is only used as a fallback if no matching option exists (defensive — should never happen for valid calls). Same for `posterPlatformFee`. On reject: send `payment-rejected` AND auto-refund the ring fee. `activePayments[callId]` is NOT created on reject — the call session never starts on our side. `deposit` and `topup` payment types are not re-validated against rates (they're credit additions, not rate claims; the authoritative `ratePerHour` was already locked in at ring time, so settlement billing is correct regardless).
- **`computePaymentOptions(rates, caller, callType, now)` shared helper** — extracted because the original v0.16.6 used `getRatesForCaller` (single applicable) which broke multi-currency validation: if a caller held CNOOBS, the resolver returned the CNOOBS rate even when the caller chose to pay HBD via the picker, and the recipient's check wrongly rejected the smaller HBD amount as "underpaid." The helper returns ALL options the caller qualifies for (one per token they hold + an HBD option from named/default lists). Both `get-all-rates` (the picker) and v0.16.6 validation use it, so the picker and the validator are now guaranteed to agree on what's a valid payment. The helper also correctly returns `{ blocked, feeRejected, message }` for those server-level rejections.
- **Bug discovered on first multi-server test of v0.16.6 (federated DM noblemage@call.completenoobs.com → guest33@v4call.com, 0.01 HBD rate):** the original v0.16.6 code used `getRatesForCaller` which picked CNOOBS as the resolver's first-token-match (noblemage holds CNOOBS). The validator saw `applicable.flat = 1.0` (CNOOBS rate) and `paid = 0.01` (HBD) and rejected as underpaid → auto-refund fired. Fixed in the same v0.16.6 cycle by extracting `computePaymentOptions` and looking up by paid currency, not by resolver first-pick. Lesson for future paid-flow validators: **the picker and the validator MUST share the same option-building code.** If the picker shows N currency options, the validator has to know about all N.
- **Caller-server notification path:** existing `dm-failed` / `payment-rejected` envelopes are reused. The caller's federation handler at `case 'dm-failed':` already exists and surfaces the reason to the local sender via `lobby-dm-error`. `case 'payment-rejected':` currently just logs — surfacing it to the caller's UI cleanly is a future polish item but is not required for the security fix to work; the refund is on-chain regardless of whether the caller's UI shows the rejection.
- **Cache implications:** `fetchRates` already caches per-username for ~5 minutes, so the extra Hive API call per paid DM / paid call ring is at most one network round-trip per recipient per cache window. Negligible in practice.
- **No federation protocol bump.** No new envelope types, no `protocol_version` change. Pre-existing peers (any version) can still be receivers — they just don't run the new validation, so their bypass surface stays open until they upgrade. New validation only protects callees on a v0.16.6+ server.
- **Why before v0.17:** v0.17 paid-expert-invites adds a third paid flow. Recipient-side enforcement should be the default architecture going forward — v0.17 inherits this pattern and doesn't need to add it bolt-on later. Per the new design rule in "Key Design Decisions" #15, all future paid flows must follow this pattern.
- **Closes the bypass class for paid DMs and paid 1:1 calls.** Open follow-ups (separate from v0.16.6):
  - Same-server `lobby-dm` handler does an explicit `paid >= rate` check too — currently a malicious browser client can underpay. Listed in backlog under "Input validation hardening".
  - Same-server `call-invite` handler — same audit. Same backlog category.
  - These are smaller surfaces than the federation ones (one operator's machine vs. potentially many) and can be batched into a future input-validation hardening sweep.
- **DM error routing + tab unread indicator (UX polish, end of v0.16.6 cycle).** When a federated paid DM was rejected by recipient-side rate enforcement, the resulting `lobby-dm-error` event was being routed via `addLobbyMsg({type:'system', text})` to the Lobby tab — but the user was on the DM tab where they sent the DM, so they saw a silent fail (the on-chain refund landed but no UI acknowledgement). Fix: `addLobbyMsg` now accepts a `context: 'dm'` parameter; DM-related system messages are routed to the DM tab's `#dm-messages` container when the DM panel is open. Three handlers updated to pass `context:'dm'`: `lobby-dm-error`, `lobby-dm-payment-required`, `text-payment-received`. Plus a small accent-coloured dot now appears on inactive tab buttons (DM tab and Lobby tab) when a new system message lands there — visible at a glance, clears when the user clicks the tab. CSS: `.lobby-tab.has-unread:not(.active)::after { content: ' •'; color: var(--accent); ... }`. `switchLobbyTab` clears the dot from the activated tab. **Net code: ~15 lines added, ~5 simplified.** All client-side; no server changes; no protocol changes. Tested across federated paid-DM flows with valid + invalid + blocked + wrong-currency scenarios — all tests pass.

### v0.16.11 polish (added on top of v0.16.10) — Federated Paid Room Invites
- **Closes the v0.16.10 cross-server gap.** v0.16.10 only enforced rates when inviter + invitee were on the same upgraded server. Federated invites still passed through the unpaid `room-invite` envelope. v0.16.11 plugs that: source server gates on rate just like the local path, populates the `payload: {}` hook with `{ payment: {...} }`, and the recipient server enforces policy + on-chain verify before delivering the popup.
- **Inviter-holds-funds (per CLAUDE.md v0.17 design lock-in).** The on-chain payment goes to the SOURCE server's escrow (ESCROW_ACCOUNT on the inviter's server), not the recipient server's. Source server stays treasurer + verifier; recipient server is router + policy enforcer only. This INVERTS the existing paid-DM federated pattern (where callee's server is treasurer). Rationale: if recipient server held the funds, a malicious recipient operator could rotate their escrow keys before settling and pocket the inviter's payment. Inviter-holds-funds removes that surface — source server only releases funds to invitee at accept, and only via direct Hive transfer to invitee's Hive account (Hive accounts are server-agnostic, so cross-server payouts are just regular on-chain transfers).
- **Source-side gate in federated `allowlist-add`.** Mirrors v0.16.10 local path: `getInviteOptions(invitee, inviter)` → free → original behaviour; paid → emit `invite-payment-required { federated:true, peerServer, options }` to inviter, modal pops, Keychain transfers to OUR escrow (`ESCROW_ACCOUNT`) with memo `v4call:invite:<inviteId>`, client retries `allowlist-add` with payment fields, server verifies on-chain, records pending entries in BOTH `pendingPaidInvites` (with `federated:true` + `invitee_server`) AND `pendingFederatedInvites` (with `paid_invite:true`), then fires federation `room-invite` with `payload: { payment: { currency, paid, memo, source_escrow } }`.
- **Recipient-side validation in federation `room-invite` handler** — per design rule #15. Five checks before delivering popup: (1) malformed payment payload → reject; (2) `source_escrow` matches peer's announced escrow from hello (catches a malicious source server claiming payment to an account it doesn't actually control); (3) target user is not blocked (via target's rates post); (4) target's platform fee ≥ this server's minimum; (5) currency + amount match an option in target's `computePaymentOptions('invite', from_user)`; (6) `verifyHivePayment` / `verifyHiveEnginePayment` confirms the on-chain transfer from `from_user` → `source_escrow` for `paid` `currency` with `memo` actually landed. Any failure sends `room-response { declined, reason: 'paid_rejected', detail }` back. Source server then auto-refunds via the same path as a user-decline.
- **Recipient popup gets the same paid badge as local invites.** When the incoming federation `room-invite` carries `payload.payment`, the server emits the local-socket `room-invite` event with `paid_invite_id: invite_id` (note: same value as the federation `invite_id` to keep the maps in lockstep), `paid_amount`, `paid_currency`. Recipient's UI shows "💜 Paid invite — @inviter sent X CURRENCY. Accept = you keep the fee (minus platform). Decline = refund to inviter." — same line as local paid invites (no client code change needed beyond what v0.16.10 already shipped).
- **Source-side settlement in `room-response` handler.** When the federation `room-response` arrives, if the source-side `pendingFederatedInvites` entry has `paid_invite: true`, dispatch by response: `accepted` → `disbursePaidInvite(invite_id)` (net to invitee via cross-Hive `sendFromEscrow`, fee to our `SERVER_HIVE_ACCOUNT`); `declined` (any reason: explicit-user, offline, paid_rejected, timed_out) → `refundPaidInvite(invite_id, reason)` + delete the canonical `user@server` entry from `r.allowlist` so the invitee can't sneak in off the paid slot. For `paid_rejected` responses, also emit a clear admin-facing lobby-info: "⚠ {peer} rejected your paid invite to @user: {detail}. Refund in flight." `break`s out of the regular admin-notification path so the inviter doesn't get duplicate messages.
- **TTL coordination.** Two parallel sweeps exist: the 60s `pendingPaidInvites` sweep (refunds after 15 min) and the 5-min `pendingFederatedInvites` sweep (prunes after 15 min). For federated entries, both now also roll back the canonical allowlist entry before refunding. `refundPaidInvite` has a status-lock so a late accept-then-decline race or a doubled sweep can't double-refund.
- **Escrow-mismatch guard (source side).** Before showing the picker for a paid federated invite, source server checks `fedInv.escrow` (from invitee's rates post) against `peer.escrow` (from the peer's signed hello). If they differ, the source server can't trust the peer to actually be able to validate a payment to that escrow (which is on the peer's chain identity), so it fails loudly BEFORE Keychain pops: "@user's rates post declares escrow @X, but {peer} controls @Y. They need to update their rates post (or switch home server) for paid invites to clear." Mirrors the paid-DM federated escrow-mismatch guard from earlier rolls.
- **No protocol_version bump.** The `payload` field is opaque to v0.3 / v0.4 peers — they ignore unknown payload contents. Un-upgraded peer combos still bypass the paid gate (the federation `room-invite` envelope they generate has `payload: {}`); to fully close the federation bypass, all peers in the mesh need v0.16.11. Mixed-version federation works fine for everything else.
- **Zero client changes.** The v0.16.10 `#invite-payment-modal`, `invite-payment-required` listener, accept/decline dispatch (`paid-invite-respond` + `room-invite-respond`), and paid-badge rendering in the room-invite popup all handle federated invites transparently — server tells client where to pay (ESCROW_ACCOUNT = OUR escrow for federated, same value as for local since both flows are inviter-holds-funds on the source server). The `paid-invite-respond` event emitted by the recipient client is a no-op on the recipient server (since `pendingPaidInvites` entries live on the source server) — it's a harmless redundant emit; the real settlement runs through `room-invite-respond` → fed `room-response` → source's `room-response` handler.
- **Known limitation — Keychain-success-then-disconnect.** Same as v0.16.10: if the inviter's Keychain transfer succeeds but their browser disconnects before the `allowlist-add` retry reaches the server, the funds are in escrow with no `pendingPaidInvites` entry → no auto-refund. Same risk profile as paid DM and paid call flows. Worth documenting in user-facing docs but not blocking for v0.16.11.
- **Net code:** ~140 lines server.js — source-side federated gate (~60), recipient-side validation block (~50), source-side settlement on response (~25), TTL coordination (~5). Zero client changes.
- **Worth testing across two real peers:** the full happy-path (paid invite from call.completenoobs.com → hive-book.com, recipient accepts, source disburses net + fee); decline path (recipient declines, source refunds); recipient-rejected path (set invitee's rate higher than source picker shows mid-flow, recipient validation fails, source refunds); offline auto-decline (target offline, source refunds); 15-min timeout (recipient never responds, source's TTL sweep refunds and rolls back allowlist).

### v0.16.10 polish (added on top of v0.16.9) — Paid Room Invites (local only)
- **Anti-spam wedge: charge to be invited to a room.** Without this, any approved user (or anyone you've previously DM'd) could spam-invite a target to dozens of throwaway rooms — the existing `room-invite` flow had no rate gate. v0.16.10 plugs that gap by reusing v4call's existing rate model: rate-editor adds an `INVITE:` field (token sections + named-list + default windows), server parses it as a flat-fee `'invite'` callType, paid invites get a Keychain modal + on-chain verify + escrow disbursement (net to invitee, fee to platform, refund on decline/timeout).
- **`INVITE:` rate field in rate post.** Added to token blocks (above TEXT) and list windows (above TEXT MESSAGE — HBD). Per-token rates apply when the inviter holds that token; per-list rates apply when the inviter matches a named list (family/friends/work/default). Same priority as voice/video/text rates: block-bypass token → token sections → named lists → default list. Free invitees behave exactly as before (no modal, no payment, immediate invite).
- **Backwards compatible.** Old rate posts (no `INVITE:` line) parse as `invite: 0` → free → no behavior change for users who haven't updated their rate post.
- **Picker / validator parity.** Same `computePaymentOptions` + `isOptionBelowFloor` filter as paid DM/call — sub-floor invite rates are treated as free (matches the v0.16.8 universal-floor architecture). Below-floor flag plumbed through to the picker so the inviter sees "rates below 0.001 min — sending free" instead of silent disagreement.
- **`pendingPaidInvites` map + 15-min TTL sweep.** Keyed by inviteId (random 12-byte hex, server-minted). Each entry: `{ room, inviter, invitee, currency, paid, memo, status, created_at, type }`. Status transitions: `pending` → `accepted` (disburse) / `declined` (refund + remove from allowlist) / `timed_out` (auto-refund via sweep) / `cancelled`. Completed entries kept for 30 min before cleanup so late accept/decline attempts return a clear "already refunded" error path.
- **`refundPaidInvite(inviteId, newStatus)` + `disbursePaidInvite(inviteId)`.** Status-locked (entry marked first, then async transfer) so concurrent accept-and-decline-at-same-time can't double-spend. Refund = gross amount back to inviter from ESCROW_ACCOUNT. Disburse = net (paid × (1 - platformFee)) to invitee + platform cut to SERVER_HIVE_ACCOUNT, both via `sendFromEscrow` with ledger entries.
- **Server-minted inviteId in the memo.** Picker emits `inviteId` to the client. Client must use it in the memo (`v4call:invite:<inviteId>`). Server verifies the memo and rejects duplicate inviteId usage. This prevents a malicious client from reusing one on-chain payment across multiple invites — each unique inviteId can be consumed exactly once.
- **Re-inviting an already-allowlisted user is a no-op.** Charge once, on the FIRST add to allowlist. Subsequent `allowlist-add` calls for the same user just re-emit the room-invite (free). Same shape as the existing free-allowlist behavior.
- **Escrow-mismatch guard.** If the local invitee's rates post declares an escrow account that this server doesn't control, the inviter is rejected with a clear error BEFORE Keychain pops up. Without this, the inviter could pay funds to an escrow whose key lives elsewhere → orphan funds, hard to recover. Mirrors the same guard in paid-DM cross-server flow (where the rate-post-escrow vs peer-escrow check exists for the same reason).
- **`room-create` deferral for paid invitees.** Async rate check runs against each local invitee; paid ones are silently DROPPED from the allowlist at room-create time, and the admin gets a per-user `lobby-info` notice: "@user requires X HBD per invite — invite them via #room's allowlist panel after creating." This keeps room-create one-shot (no mid-flow modal interruption) and routes all paid invites through the `allowlist-add` flow which has the modal.
- **Recipient-side popup gets a paid-invite badge.** When `paid_invite_id` is present in the `room-invite` payload, the popup renders an extra line: "💜 Paid invite — @inviter sent X CURRENCY. Accept = you keep the fee (minus platform). Decline = refund to inviter." Lobby system message also tags the invite with the amount. Recipient's `acceptInvite()` / `declineInvite()` dispatch a new `paid-invite-respond` event before the existing federated `room-invite-respond` / local-enter-room flows.
- **`paid-invite-respond { paid_invite_id, response }` socket handler.** Only the actual invitee can resolve their own paid invite (ownership check). Accept → `disbursePaidInvite`. Decline → `refundPaidInvite('declined')` + remove from allowlist + `emitRoomInfoToMembers` + `broadcastRooms`. Decline removes from allowlist so a malicious recipient can't "decline + refund + sneak in later" off the same paid slot.
- **Client modal: purple-accented `#invite-payment-modal`.** Reuses the existing `.payment-box` + `.pm-cur-btn` CSS classes from the call/DM payment modal. Currency picker with balances; total updates as the inviter selects a currency. Cancel button dismisses. Confirm fires `requestTransfer` (HBD/HIVE) or `requestCustomJson` (Hive-Engine tokens), then re-emits `allowlist-add` with the payment fields. On Keychain cancel/error, modal closes and a system message explains.
- **What's NOT in v0.16.10 (queued for v0.16.11):** cross-server paid invites. The federation `room-invite` envelope's `payload: {}` hook is the v0.16 forward-compat slot designed for exactly this — v0.16.11 will populate it with `{ payment }` and add recipient-side rate enforcement on the federation `room-invite` receive path (per design rule #15, mirroring the v0.16.6 paid-DM federation pattern). Auto-refund on cross-server decline/timeout via `sendFromEscrow` from the source server's escrow. Today, attempting `allowlist-add @user@peer.com` to a peer hosting a user with an invite rate will... still work as free, because the inviter's server only checks LOCAL rate gates in v0.16.10 (federation path hasn't been updated yet). The cross-server bypass surface is real but small (it only matters when the peer's user has invite rates set), and explicitly documented as deferred.
- **Net code:** ~30 lines in rate-editor.html (INVITE field in tokens + windows, output + parser, defaults), ~180 lines in server.js (helpers, gates, TTL sweep, paid-invite-respond handler, escrow-mismatch guard), ~120 lines in client (modal HTML + CSS + invite-payment-required listener + Keychain flow + paid-invite popup additions + paid-invite-respond dispatch from accept/decline). No federation protocol bump.
- **Migration note for existing users:** the change is opt-in. Users who don't update their rate post pay nothing extra and accept invites as before. Users who set an `INVITE:` rate begin charging immediately on next post update. The rate-editor's "Load From Hive" flow reads the new `INVITE:` field if present; the "Generate Output" emits it on save. Existing rate posts without `INVITE:` are treated as `0` (free).

### v0.16.8 polish (added on top of v0.16.7) — Universal Precision Floor (Path C)
- **Picker / validator agreement on rates below the precision floor.** Background: server-side checks like `if (paid >= 0.001)` and `if (textRate >= 0.001)` use 0.001 as "this is paid." For high-precision tokens (e.g. SWAP.BTC, 8 decimals), users could set ring/text rates below 0.001 (e.g. 0.000001 SWAP.BTC), the picker would show the option as paid, and the server would treat the actual call/DM as free — picker and validator disagreed. Worse: the disbursement pipeline uses `.toFixed(3)` everywhere, so even if we patched the validator, calleeNet would round to 0 and funds would get stuck in escrow. **Path C chosen** — universal floor, picker filters honestly. Path B (per-currency floor with full disbursement refactor) preserved as a documented future upgrade if there's demand for sub-millicent token rates.
- **`RATE_FLOOR = 0.001` constant.** Defined near `PLATFORM_FEE` with a comment explaining the choice and the Path B upgrade path.
- **`isOptionBelowFloor(opt)` helper.** Returns true if any nonzero rate field on the option is below `RATE_FLOOR` — `flat` for text options; `ring`, `connect`, `rate` for voice/video options. Options with all rate fields = 0 are genuinely free, not "below floor" — no warning needed for those.
- **`computePaymentOptions` filters below-floor options + returns `belowFloor` flag.** New internal `pushOrFlag(opt)` helper is the only path that adds an option to the result array — calls `isOptionBelowFloor`, sets `belowFloor=true` if filtered. Both token sections and the HBD/named-list option now route through `pushOrFlag`. Return shape extends: `{ options, blocked, feeRejected, belowFloor, message }`.
- **`getRatesForCaller` skips below-floor options.** All three return paths that build a `buildCallRateResult` (block-bypass token, normal token loop, named/default list) now check `isOptionBelowFloor` on the candidate result; if below floor, log + return `null` (treats as free, matching what the picker shows). Validator paths (`lobby-dm` handler, federation `dm` and `payment-verified` handlers) use the same resolver, so they also see "free" when a rate is below floor — no separate threshold check needed.
- **`get-all-rates` socket handler threads `belowFloor` through.** The `free: true` and `free: false` response branches both now include `belowFloor: result.belowFloor || false`.
- **Picker UI surfaces the below-floor warning.**
  - **DM panel rate badge** (`openDmPanel`): when `belowFloor && options.length === 0`, the badge reads `⚠ rates below 0.001 min — sending free` (with a hover `title` explaining). Without `belowFloor`, the existing "Free" badge stays unchanged.
  - **Call flow** (`initiateCall`): when `response.free && response.belowFloor`, the "Checking @user's rates…" lobby system message follows up with `⚠ @user's call rates are below this server's processable minimum (0.001) — calling for free.` instead of the regular "rates show free for this time window" message.
- **Why this also closes the disbursement-stuck-funds class.** Without the picker filter, validator-only fixes would let users pay sub-floor amounts that the disbursement code's `.toFixed(3)` then rounds to 0, leaving funds permanently in escrow. By gating at the picker level, no such payment ever happens — the user is told up front the rate is unprocessable.
- **No federation protocol bump.** Server-side change only. The `belowFloor` flag is local to the `get-all-rates` callback; federation envelopes (`dm`, `payment-verified`) unchanged. Mixed-version federation works fine — peers without v0.16.8 just don't filter, and any below-floor payment they forward gets verified by us as free regardless (the recipient-side `getRatesForCaller` returns null for below-floor rates, so the federation `dm` handler treats `paid >= 0.001` as the threshold, which the rate's `flat < 0.001` doesn't meet).
- **Path B upgrade path (deferred).** To support sub-millicent token rates (e.g. 0.0001 SWAP.BTC ring fee = ~$5–10 USD), replace `RATE_FLOOR` with `getCurrencyFloor(currency)` (cached lookup of token precision via Hive-Engine `findOne` on `tokens` contract) AND replace every `.toFixed(3)` in the disbursement pipeline (`processCallEnd`, `processFederatedCallEnd`, `lobby-dm` handler payout calculations, federation `dm` handler payout calculations) with `parseFloat(amount.toFixed(precision))` per currency. ~15 sites across server.js. Deferred because v4call's realistic-amount range — production SWAP.BTC ring fees are 0.001 BTC and up (~$50–100 USD) — doesn't currently need sub-millicent precision. Path B becomes worth doing if a major use case demands it.
- **Net code:** ~50 lines added in server.js (constant, helper, refactored option-building, return-shape extensions), ~20 lines updated in client (DM panel + call flow warning surfaces).

### Federation (v0.4)
- **Server-to-server WebSocket:** persistent connection on `/federation`, domain tiebreaker so only the lower-domain initiates outbound (avoids flapping)
- **Verify.json domain proof:** signer page produces a Hive-key-signed JSON file hosted at `/.well-known/v4call-server.json`. Discovering servers fetch + verify the signature against the signer's posting pubkey from Hive.
- **Hive directory:** server-announce page produces a `v4call-server` tagged Hive post. Discovery scanner queries `condenser_api.get_discussions_by_created` every 2h.
- **Approval gate:** verified peers must be explicitly approved. Seed list from `FEDERATION_PEERS` env auto-approves on startup; manual approvals via `POST /admin/peers/approve` persist to `approved-peers.json`.
- **Cross-server presence:** federated users appear in the lobby with a server-domain badge.
- **Cross-server DMs:** ciphertext relayed via federation `dm` message; server never sees plaintext. Supports paid DMs (recipient's server re-verifies on-chain, disburses from its own escrow).
- **Cross-server 1:1 calls:** caller's server hosts the room, callee's browser opens a temporary cross-server Socket.io connection for WebRTC signalling. Media still peer-to-peer.
- **Cross-server payments:** caller pays callee's escrow on Hive. Caller's server verifies and forwards `payment-verified`. Callee's server re-verifies, disburses callee-net + platform-fee + refund (refund as cross-server Hive transfer from its own escrow back to the caller).
- **Escrow-mismatch guard:** if a callee's rates-post escrow doesn't match the peer's announced escrow, paid calls fail loudly with a clear error explaining the mismatch.
- **Cross-server room invites:** admin types `@user@peer.com` into the room's allowlist; server validates target server is approved + connected + on protocol_version >= 0.4; sends `room-invite` over federation. Receiving server delivers a popup with a source-server badge. Accept/decline flow back as `room-response`. Pending invites prune after 15 minutes.
- **Cross-server room join:** accepting a federated room invite opens a temp Socket.io from the joiner's browser to the host server (same direct browser↔server pattern 1:1 federated calls already use). `homeServer` in the `join` payload lets the host server match the joiner against the room's canonical `user@server` allowlist entry. Multi-party WebRTC media is peer-to-peer as ever. Federated members appear in the room user-list and on video tiles with a `@hive-book.com`-style server badge. Token-gating works across federation (chain-side balance check is peer-agnostic). Banlist + allowlist-remove auto-kick honour canonical form. Federation peer drop while a federated user is mid-room → host server immediately evicts them. Temp-socket drop on the joiner side gates on `'io server disconnect'` only — transient blips let Socket.io reconnect.
- **`protocol_version` gate:** explicit version field added to the hello envelope. Allows incremental wire-format additions (v0.4, v0.5, ...) without breaking older peers — old peers ignore unknown message types, new features only activate when both ends advertise the required version.

## Key Design Decisions

1. **Separate databases:** v4call-chat.db is separate from v4call-ledger.db. If chat storage is exploited, the payment ledger is untouched. Only the server writes to the ledger.

2. **Platform fee is a minimum, not a fixed rate:** Server operators compete on fees. Users shop around. This is now a real free market across federated servers.

3. **Encryption uses Hive posting keys via hivecrypt:** This means Keychain login users need to enter their posting key separately for encryption. There's no workaround — Keychain deliberately never exposes private keys.

4. **Hive-Engine API is at `/rpc/contracts`:** The old endpoint `/contracts` returns HTML and is dead. This was a painful debugging session. Do not change this URL.

5. **Token payment verification uses balance checks, not transfer history:** The Hive-Engine `transferHistory` table is not reliably queryable via the contracts RPC. Instead, we verify that the escrow account's token balance is sufficient. The payment was already signed via Keychain.

6. **`docker compose down` is required before rebuilding:** Without this, Docker reuses the old container even after `docker compose build --no-cache`. This caused hours of debugging where changes weren't taking effect.

7. **Rooms are ephemeral:** When the last person leaves, the room and all its stored messages are deleted from the database. This is deliberate — rooms are not meant to persist.

8. **All three buttons (voice, video, DM) use inline SVG icons:** No image files, no emoji. The SVGs inherit colour from CSS via `stroke="currentColor"`.

9. **Federation domain tiebreaker:** When both peers connect outbound at the same time, only the lexicographically-smaller domain keeps its outbound. The other peer goes "passive mode" and accepts inbound only. This avoids the flapping bug where both sides closed the other's connection. See `fedShouldInitiate()`.

10. **Federation handshake is fail-closed:** A peer must (a) verify cryptographically, (b) be in `approvedPeers`. Anything else closes the socket with a clear log message.

11. **Per-socket message ordering on federation:** Each federation WebSocket has a Promise queue chain so messages are processed strictly in order. Without this, presence arriving while hello was still verifying got silently dropped.

12. **Escrow account must match the server holding its key:** A user's `v4call-rates` post declares one `ESCROW:` account. That account's active key must live on the server where the user is currently logged in. Mismatch = paid flows fail because the destination server can't disburse from an escrow it doesn't own. The federation hello announces each server's `ESCROW_ACCOUNT` so the caller side can detect this mismatch and emit a clear error.

13. **Caller's server is the verifier and router; callee's server is the treasurer:** For cross-server paid calls/DMs, the caller's server *only* verifies on-chain payments and forwards a notification. It never disburses cross-server escrows. The callee's server (which holds the escrow key) does all disbursement. Both sides re-verify the on-chain payment for safety.

14. **The four operator pages are intentionally standalone:** rate-editor, server-sign, server-announce, admin-peers. They sign with the operator's Hive key (via Keychain or paste) — the key never reaches the v4call server. Same security pattern as the rate editor.

15. **Recipients enforce their own rules.** The recipient's home server is the only server fully trusted to enforce the recipient's policies (block-list, rate, platform-fee minimum, currency / token-gate / time-window). Caller-side servers are message couriers + payment witnesses — they may pre-check rates for UX (showing the caller what to pay) and verify on-chain payments for first-pass filtering, but they are NEVER trusted as the sole policy enforcer. This is the standard federated-system pattern (email spam filtering, Mastodon blocks, XMPP / Matrix permissions all use it). Implemented for paid DMs and paid 1:1 calls in v0.16.6 — the federation `dm` and `payment-verified` handlers re-fetch the recipient's rates and re-validate before disbursing. On reject: refund from our escrow back to the caller. **Apply the same pattern to every future paid flow** (e.g. v0.17 paid expert invites — even with inviter-holds-funds, the recipient's server should still validate the offer terms are sensible before the expert auto-accepts).

## Known Gotchas and Debugging Tips

- **Duplicate `FEDERATION_PEERS=` lines in `.env` silently dedup — dotenv is last-wins.** Each operator's `.env` MUST list peers as a single comma-separated line, e.g. `FEDERATION_PEERS=wss://hive-book.com/federation,wss://v4call.com/federation`. Writing two `FEDERATION_PEERS=` lines causes `process.env.FEDERATION_PEERS` to contain ONLY the second URL — the first is silently dropped, no log warning at boot (v0.16.18 and earlier). Caught in production 2026-05-28 in a three-server mesh: cnoobz@hive-book.com flickered in and out of call.completenoobs.com's lobby (visible via Nostr presence, no WSS link because both servers had this dup-line bug, so they appeared and aged out every 5 min). DMs/calls between those two looked broken at random. Combined with the domain tiebreaker (lex-smaller initiates), the dup-line bug can knock out specific peer-pairs while leaving others working — making it look like "fed is partially broken" instead of "config is wrong". **v0.16.19+ adds a boot-time scan that logs `[config] ⚠ multiple FEDERATION_PEERS lines in .env — dotenv keeps only the LAST. Use comma-separated form.`** so the next operator sees the bug within seconds. Same pattern applies to any other env var documented as comma-separated. See FED-RECOVERY-NOTES.md Lesson 11 for full forensics. **The bigger meta-lesson — "WSS-disable-during-Nostr-test trap":** any time you turn off WSS fed to isolate-test Nostr, write a one-line note next to the change AND a follow-up task to re-enable. Nostr presence masks WSS being down for everything except actual cross-server DMs/calls — easy to forget about for weeks.
- **"Appear offline" / invisible still receives room invites + DMs.** The `invisible` flag on `lobbyUsers[username]` only affects PRESENCE (the user is hidden from the lobby user-list snapshot + federation `presence` envelopes). It does NOT affect deliverability — `lobbyUsers[target]` lookups for direct deliveries (room invites, paid invites, DMs) ignore the `invisible` flag, so messages still reach the user's socket and the popup/notification fires. Confirmed in v0.16.13 testing 2026-05-22 (noblemage marked invisible, received a federated paid-invite popup normally). **By design**: presence privacy and deliverability are different concerns — invisible = "don't broadcast my online state", not "don't ring my phone". If a future "truly offline mode" (auto-decline invites + return DM errors when invisible) is wanted, it's a separate `appearOffline` flag — don't overload `invisible`.
- **`rate-editor.html` "Post failed: unknown error" is usually NOT a v4call bug.** Two common Hive-side causes: (1) Hive enforces a **~5-minute gap between posts from the same account** — if you posted (rate update OR a regular blog post) less than 5 min ago, the broadcast fails. Wait and retry. Confirmed live during v0.16.10 testing 2026-05-21 — the "fix" was patience, not code. (2) **Low Resource Credits (RC)** on the posting account, especially fresh accounts with no staked Hive Power — broadcast fails until RC regenerates (~5 days) or someone delegates HP. Check at `https://hivestats.io/@username`. Rate-editor's post-failure handler dumps the full Keychain response object to browser DevTools Console so the real error is visible (the `response.message` field is often empty for these Hive-level rejections, hence the "unknown" fallback).
- **Changes not appearing after deploy:** Always `docker compose down && docker compose build --no-cache && docker compose up -d`. Never just `docker compose restart`.
- **Hive-Engine balance check returning 0:** Check the API URL is `https://api.hive-engine.com/rpc/contracts` not the old `/contracts` endpoint.
- **Token symbol case sensitivity:** The symbol in the rates post must match Hive-Engine exactly (usually all uppercase).
- **SQLite permission errors:** The app runs as UID 1000 inside Docker. Fix with `chown -R 1000:1000 ./data/logs/` on the host.
- **Certbot failing:** Must use `--entrypoint certbot` flag or Docker runs the renewal loop instead of `certonly`.
- **Nginx cert crash loop:** Never put HTTPS config in nginx before the cert exists. Start HTTP-only, get cert, then add HTTPS.
- **Sign error on login:** The `hivecrypt` library needs the posting key as a string. Keychain mode doesn't have this, so signing falls back to `requestSignBuffer`. Hash type wrapping fixed in v0.11 by using `dhive.cryptoUtils.sha256` instead of raw Uint8Array.
- **`.well-known` directory must use a hyphen** — `.well_known` (underscore) is wrong (RFC 8615). The verify file must be at `public/.well-known/v4call-server.json` exactly. Wrong filename or directory = federation handshake 404 = federation broken.
- **v4call-server.json placeholder:** The repo ships a tiny placeholder at `public/.well-known/v4call-server.json`. Each operator must overwrite it with their own signed file from `/server-sign.html` before federation works. Commit your generated file so fresh installs include it.
- **Federation flapping:** If you see endless `Outbound connected → Disconnected` cycles, the domain tiebreaker may be misconfigured or the peer's v4call-server.json isn't matching. Check both sides' logs for `✓ Peer verified` or `✗ Peer verification failed`.
- **Federated paid call/DM fails silently:** Likely an escrow mismatch — the user's rates post points at an escrow not controlled by their home server. Caller-side server emits a clear `lobby-dm-error` or `call-failed` explaining this once the federation hello has exchanged escrow info.
- **Hive node failures look quiet:** Fixed in v0.12 — `hivePost` now logs HTTP status, JSON-RPC errors, and a raw body preview when a node returns 200 OK without `result`. If you ever see this regress, check `server.js`'s `hivePost` helper.
- **`condenser_api.get_discussions_by_created` `limit` cap is 20:** Hive nodes enforce this with `Assert Exception` on values > 20. The discovery scanner's `limit` was 50 in v0.11 and silently failed on every node; fixed in v0.12. If you add another `get_discussions_by_*` query, keep `limit ≤ 20` and paginate via `start_author + start_permlink` if you need more.
- **Browser cache hides client fixes:** After a `docker compose ... up -d` of new client code, mobile Safari/Brave can keep serving the cached `index.html` for hours. If a fix that should be visible isn't, clear browser history/site data on the device first.
- **iPhone Hive Keychain doesn't inject `window.hive_keychain`:** iOS Safari and iOS Brave (also WebKit) don't allow extensions that inject scripts into pages. The Hive Keychain *mobile app* exists but can't talk to web pages the way the desktop extension does, so paid actions fall through the "Keychain required" error on iOS. **Not a v4call bug.** Future workaround options: HiveSigner web flow (`https://hivesigner.com/sign/transfer?...`) as a fallback when `window.hive_keychain` is undefined; or `@hiveio/keychain-sdk` for QR/deep-link handshake to the mobile app. See "Future Work" for the planned approach.
- **`element.style.display = ''` does NOT override a CSS `display:none` rule.** Setting an empty string just *removes* the inline declaration; the cascade re-applies whatever the stylesheet says — which for v4call's hidden-by-default buttons is `none`. This bit us hard from v0.11 to v0.14.5: four header buttons (`#leave-room-btn`, `#popout-btn`, `#export-room-btn`, `#end-room-btn`) were never visible. The working pattern is the `.shown` class that `#enable-mic-btn` etc. use — `#id { display: none; }` + `#id.shown { display: inline-block; }` (the compound selector has higher specificity than the ID alone), with JS toggling via `classList.add('shown')` / `classList.remove('shown')` (or `classList.toggle('shown', cond)` for conditional cases). When adding a new hidden-by-default button, **use the `.shown` class pattern, never `style.display = ''`.**
- **Avoid duplicate property declarations in the same CSS rule.** `#call-cost-ticker` had `{ display:none; ...; display:flex; ... }` from v0.11 onwards — last-wins meant it was always `flex` and the `.active` modifier was a no-op (End Call button always visible regardless of ticker state). When CSS rules grow long, scan for repeated property names before pasting more.
- **A WebRTC offer with no `m=` lines forces an answer with no `m=` lines.** From v0.12 (when text-only room joins shipped) until v0.15: text-only joiners' `createPC` had no `localStream` so no tracks got added → no transceivers → `createOffer()` produced an SDP with zero media sections. Existing peers' `createAnswer()` mirrors the offer's m-lines (per JSEP), so the answer was also empty. Result: existing peers' tracks were attached to the new PC but never sent — text-only joiners couldn't see anyone's cam or hear their mic until they enabled their own. Fix: **always ensure both audio + video transceivers exist** in `createPC` — `if (!haveAudio) pc.addTransceiver('audio', { direction: 'recvonly' })` + same for video. Chrome's `addTrack` algorithm reuses unused recvonly transceivers, so the existing enable-cam-mid-room path keeps working without duplicate m-lines. **Lesson:** when adding `addTrack` conditionally based on local media availability, also add `addTransceiver(kind, { direction: 'recvonly' })` for the kinds you're not sending — otherwise you can't receive that kind either.
- **`git fetch --all && git reset --hard origin/main` will clobber operator-specific files.** Specifically `nginx/v4call.conf` (where the operator's domain replaces the placeholder `v4call.com`) and `public/.well-known/v4call-server.json` (the operator's signed verify file from `/server-sign.html`). Both ship as templates/placeholders in git; a hard reset reverts them to the shipped versions, which breaks HTTPS (wrong domain in nginx config) and federation (v4call-server.json reverts to placeholder). **Operators must back up these two files before updating** — see WalkThrough.wiki "Updating to a new version" for the recommended `cp ... bk....` flow. When proposing repo updates to the user, always remind them to back up these two files first.
- **Rate post precision floor: any rate below 0.001 is treated as free.** Server-side `RATE_FLOOR = 0.001` (defined near `PLATFORM_FEE` in server.js) is the universal threshold for "this is paid." Applies to all currencies — HBD, HIVE, custom Hive-Engine tokens. For high-precision tokens like SWAP.BTC (8 decimal places), the minimum settable rate is 0.001 of the token. Production SWAP.BTC ring fees are typically 0.001 BTC and up (~$50–100 USD) so this is a sensible production minimum. **Picker now agrees with the validator** (v0.16.8): `computePaymentOptions` filters out below-floor options and returns `belowFloor: true` when it dropped any. Picker UI surfaces a clear warning ("⚠ rates below 0.001 min — sending free") instead of silently disagreeing with the server. **To support sub-millicent token rates** (e.g. 0.0001 SWAP.BTC = ~$5–10 USD), do the Path B upgrade documented in the v0.16.8 polish section: replace `RATE_FLOOR` with per-currency `getCurrencyFloor(currency)` (cached Hive-Engine `findOne` lookup) AND replace every `.toFixed(3)` in disbursement code with per-currency precision. ~15 sites in server.js. Originally surfaced 2026-05-04 (SWAP.BTC ring-fee testing); v0.16.8 closed the picker/validator disagreement bug.
- **SWAP.* tokens (SWAP.BTC, SWAP.DOGE, SWAP.ETH, etc.) work as payment currencies out of the box but have important caveats.** They're 1:1 wrapped tokens managed by tribaldex.com / hive-engine.com — meaning a custodian holds the real underlying coin and mints the SWAP version on Hive-Engine. **Counterparty risk: if the wrapper service shuts down or is compromised, the SWAP token can de-peg from 1:1 with the underlying.** Plus withdrawal fees back to the native blockchain are non-trivial (e.g. minimum withdrawal 0.01 SWAP.BTC). For small in-platform payments, SWAP.* is fine; for large amounts users should be aware of the wrapper risk and the redemption fees. Worth surfacing this caveat to operators / users in any docs that promote SWAP.* as a payment option.
- **`/admin-peers.html`: click "🔄 Load / Refresh" first when a peer is stuck on `✗ unverified`, NOT "🔍 Rescan Hive now".** The two buttons do different things — Load/Refresh re-pulls the current peer state (fast, no Hive calls) and shows the latest verification result; Rescan kicks off a fresh Hive discovery scan (slow, every-2h cycle). When verification fails on a transient network blip (e.g. `Cannot fetch v4call-server.json: The operation was aborted due to timeout`), the server retries verification on its own schedule — Load/Refresh is the cheap way to see when it succeeds. Confirmed live during the 3-server federation rollout in v0.16. The Approve button is hidden by design when a peer is unverified — there's nothing to fix on the unverified peer's side once v4call-server.json is real and reachable; just refresh until the chip flips to `✓ verified` and the button appears.
- **Uploads-tab enrichment is home-server-local (known, deferred).** The 📦 Uploads tab labels each gate upload with filename + "in #room" from the `upload_index` table. That row is written by whichever server's `room-attachment`/`dm-attachment` handler runs — which for a **federated** room is the room **HOST**, not the uploader's **home** server. The tab reads `my-uploads-context` from the user's **home** server, so a federated participant who uploaded in a room hosted elsewhere sees a bare 🔒 row (the gate still lists the pin — gate is shared — just without the label). Works fine when uploader's home == room host. Confirmed 2026-06-04 (cnoobz@hive-book.com in a v4call.com-hosted room → row landed on v4call.com, not hive-book.com). Deferred per owner. Fix later via client-side localStorage self-record (same-browser) and/or federation-forwarding the index row to the uploader's home server. See `feature_plans/uploads-tab-briefing.md` "Known limitation".

## Security Assessment (from VS Code review)

### Current Posture: Moderate

**Strengths:** Parameterized SQL queries, encrypted chat storage (ciphertext only), on-chain payment verification with multi-node fallback, escrow-based payment flow, non-root Docker container, HTTPS enforcement, federation domain proof via Hive-key signature.

**Known Weaknesses (accepted for v0.11, fix before high-value production):**

1. **Username spoofing (HIGH):** `lobby-join` trusts client-provided username/pubKey without server-side Hive verification. Doesn't affect payments (verified on-chain) but allows message impersonation.
   - *Fix:* Server-side challenge-response identity verification on join.

2. **No rate limiting (HIGH):** Socket.io connections and messages have no limits. Vulnerable to connection flooding and message spam.
   - *Fix:* Socket.io middleware rate limiter, Nginx connection limits per IP.

3. **No server-side signature verification:** Chat messages carry signatures but the server doesn't verify them — verification happens client-side only.
   - *Fix:* Verify signatures server-side before relaying.

4. **Input validation gaps (MEDIUM):** Usernames, room names, and memos aren't length-limited or character-validated server-side. SQL injection is prevented by parameterization, but malformed data could cause client-side issues.
   - *Fix:* Validate inputs (alphanumeric + limited special chars, max lengths).

5. **Unencrypted SQLite at rest (MEDIUM):** Both databases are unencrypted on disk.
   - *Fix:* Consider SQLCipher for production deployments.

6. **Debug endpoints exposed (LOW):** `/debug-state` and `/debug-rates/*` are publicly accessible.
   - *Fix:* Auth-protect or remove in production.

7. **Escrow key in env var (LOW):** Standard practice but no HSM/vault integration.
   - *Long-term:* Docker secrets or vault integration.

8. **Token balance caching (LOW):** 5-minute TTL could allow stale balance reads.

9. **Federation inbound trust (MEDIUM, federation-specific):** A peer that publishes a valid signed v4call-server.json + Hive announce can connect to any v4call server (subject to operator approval). Once approved, federated peers send presence/DMs/call invites we trust the wire format of. Worst case: an approved-then-malicious peer can inject fake presence (UI noise) or relay tampered ciphertext (recipient detects via signature verification client-side). Cannot steal money — payments are still on-chain verified.

**Not a risk:** CORS/CSRF (WebSocket-based), payment verification (on-chain, robust), encryption (client-side hivecrypt with Hive keys).

**v0.16.11 — original design (kept here for reference; shipped as above):**

**Closes the federation bypass in v0.16.10.** Today, paid invites only enforce when the invitee is local on the same server as the inviter; federated invites still go through the unpaid `room-invite` envelope. v0.16.11 will populate the v0.16 forward-compat `payload: {}` slot in the `room-invite` envelope with `{ payment: { currency, paid, memo, inviteId } }` and add recipient-side rate enforcement on the federation `room-invite` receive path (per design rule #15, mirroring the v0.16.6 paid-DM pattern). On reject the source server auto-refunds from its own escrow (inviter-side hold pattern — mirrors how the inviter paid into their own server's escrow). On accept the recipient server disburses (net to invitee + platform fee to recipient server's operator). On decline / 15-min timeout the source server refunds.

**Locked-in design (drafted alongside v0.16.10):**
- **Inviter-holds-funds model** — same as the v0.17 paid expert invite pattern. Inviter pays into their OWN server's escrow on Hive. This INVERTS the existing paid-DM cross-server pattern (where callee's server is treasurer). Rationale: if the funds lived in the invitee's server's escrow but the invitee declined cross-server, the source server has no key to refund — it would have to ask the recipient server to refund, adding a trust hop. With inviter-holds-funds, the source server has both verification (the on-chain transfer was to its own escrow) AND disbursement authority. Recipient server is router + policy enforcer only.
- **Federation envelope** — `room-invite` payload becomes `{ payment: { currency, paid, memo, inviteId } }` when paid (empty `{}` when free, same as v0.16/v0.17 forward-compat). New `room-response` reason field `paid_rejected` for recipient-side enforcement rejections (block-list, fee-minimum, underpaid, escrow-mismatch).
- **Recipient-side enforcement** (per design rule #15) — on receiving a paid `room-invite`, the recipient's server re-fetches the invitee's rates, re-validates (block-list, platform-fee minimum, paid amount ≥ required rate, currency matches an offered option), and only forwards the popup if valid. On invalid, sends `room-response { response: 'declined', reason: 'paid_rejected', detail }` back to source; source server auto-refunds and surfaces the reason to the admin.
- **Accept disbursement** — source server fires `paid-invite-respond accepted` → disburses from its own escrow → `sendFromEscrow(invitee, net, ...)` (cross-server Hive transfer to the invitee's account on the recipient server's chain identity) + `sendFromEscrow(SERVER_HIVE_ACCOUNT, fee, ...)` to its own operator.
- **No protocol_version bump** — the `payload` field is already opaque to v0.3 / v0.4 peers. v0.16.11 peers populate it; older peers ignore it (and the invite goes through as free on the old peer's side — same bypass as v0.16.10 cross-server, but only on un-upgraded peer combos).
- **Estimated scope:** ~120 lines server.js (recipient-side validation in federation `room-invite` handler, source-side accept/decline disbursement, cross-server refund flow), zero client changes (the client-side modal + retry logic from v0.16.10 already handles federated targets the same way). One session.

### v0.17 / federation v0.5 — Paid Expert Invites (2–3 sessions)
**The seed feature.** Reverse the v4call payment direction: instead of "caller pays callee for receiving", the room admin pays an invited expert for joining and contributing. Use case from the user's own framing: when working on a project you need short bursts of expert help on (a language, a tool, a domain you'll touch for days or weeks then drop), some experts only show up if there's payment or token reward. v4call already supports HBD + custom Hive-Engine tokens (e.g. CNOOBS), so this slots in naturally — invite the expert, agree on terms, pay in whichever currency you've negotiated. **Not a marketplace, not a paid-consultancy platform** — a payment primitive for inviting domain experts to a specific session. Requires v0.16 federated rooms to land first.

**Locked-in design:**
- **Payer model — admin only, one paid offer at a time per inviter (v0.17 first build).** The room admin pays the expert from their own escrow. Splitting between members deferred (see Deferred section). Expanding to "anyone in room with funds can invite" + multiple concurrent paid offers is a post-v0.17 follow-up — keeps the first build simple and validates the core flow before adding global escrow reservation accounting.
- **Inviter holds the funds, NOT the expert.** Upfront cap (connectFee + maxDuration × ratePerHour) is paid by the admin into their OWN server's escrow on Hive. **Why:** if the cap lived in the expert's escrow (mirroring the 1:1 paid call pattern), a malicious expert could change their escrow account's keys mid-session and abscond with the pre-paid funds. Inviter-holds-funds eliminates that rug-pull surface — expert only receives what admin's server disburses, when it disburses. **This INVERTS the existing 1:1 paid call cross-server flow** (see "Cross-server escrow flow" below).
- **The invite IS the negotiated contract.** Admin sets `connectFee + ratePerHour + currency + maxDuration` in the invite payload. Expert sees explicit terms before accepting — no surprise rates. Accept = consent to those exact terms; expert's normal rates post is ignored. Optional client helper: pre-fill the offer with the expert's posted rates so admin can negotiate from there.
- **Each offer is its own contract — no special re-invite logic needed.** If the expert disconnects mid-session for any reason, the contract settles for actual time elapsed. If admin wants the expert back, that's a fresh invite — admin can set the new offer's connect fee to anything (including 0) at offer-build time. No "waive on re-invite" toggle in the data model; just two separate offers. Connect fee for each offer is bundled with that offer's final settlement (NOT charged on join), so a session that ends after 30 seconds doesn't pay the full connect fee + 30s if admin doesn't want it to (they set the terms).
- **Termination flows** — voluntary leave / kick / room-end / connection-drop all settle the same way: final bill = connect fee + (actual duration × ratePerHour), capped at `maxDuration × ratePerHour`. 30-second grace period for reconnect (mirrors existing call disconnect handling) before settling.
- **Same-room model** — expert joins as a normal participant with a 💎 "paid expert" badge in the user list. Sees and speaks with everyone. Not a sub-room or special bubble.
- **Cross-server escrow flow — INVERTED from 1:1 paid calls.** Admin's server is **treasurer + verifier**: cap held in admin's-server-escrow on Hive, admin's server disburses to expert at settlement (cross-server Hive transfer if federated), refund of unused cap stays in admin's escrow → returned to admin. Expert's server is **router only**: forwards the invite via federation `room-invite` (paid `payload` per v0.16 forward-compat hook), delivers the popup, relays the join. Expert's server **does not** touch funds at any point — no key required for the expert's escrow on the expert's server. Inverts the existing 1:1 federated paid call pattern (where callee's server is treasurer); the rationale is the rug-pull protection in the "Inviter holds the funds" bullet above. **Implementation note:** don't blindly copy `processCallEnd` for settlement logic — disbursement direction is reversed, and there's no cross-server refund needed (refund stays local to admin's server).
- **Expert UI** — earnings ticker mirroring the existing caller's spend ticker (counts up instead of down). Clear "✓ Accept terms" / "✗ Decline" modal with the explicit rate breakdown.
- **Admin UI** — offer-builder modal at invite time (currency picker, fee fields, max duration), live-spend ticker per paid invitee while session runs.

**Estimated scope:** ~300 lines server (paid invite flow, per-expert escrow tracking, end-of-session settlement), ~150 lines client (offer-builder, accept modal, expert earnings ticker). 2–3 sessions.

**Why this is the seed feature:** paid 1:1 calls (current v4call) cover "callers paying me for my time." Paid expert-invites flip the direction — "I can offer payment to bring an expert into a room I'm working in." Different category, different value per session. On-chain settlement is genuinely useful here — transparent, instant, no chargebacks, supports custom-token payments (e.g. paying an expert in a project's own Hive-Engine token). Marketplace / discovery / trust layers (reviews, expert directories) are explicitly out of scope for v0.17 — this build ships the payment primitive only. The rest is a possible future side-quest.

### v0.18.5+ (provisional, phased) — Nostr + Lightning Bitcoin integration
**Multi-version feature, captured here as a forward-looking plan. Origin: brainstorm session 2026-05-03.** Goal: extend v4call's Hive-based identity + payment system to interoperate with the Nostr ecosystem (decentralised event broadcast) and the Lightning Bitcoin payment rail. v4call stays Hive-first; Nostr + Lightning are additive layers that make v4call users more reachable, give independence-fallback if v4call infrastructure is down, and provide a tipping channel that doesn't compete with v4call's paid-DM/call rate gate.

**📐 Server-side Nostr architecture is captured separately in [NOSTR-DESIGN-NOTES.md](NOSTR-DESIGN-NOTES.md)** (added 2026-05-05). That doc covers the federation-discovery side of Nostr: per-server keypair (`data/nostr-key.json`, generated on first boot), `NOSTR_PUBKEY:` line cross-referenced in the existing Hive `server-announce` post (Hive = trust root, Nostr = speed layer), `kind 30078` parameterized replaceable events with `d=domain` tag, server-side only (no browser-side relay connections), strfry relay with policy plugin enforcing identity-gated writes, three gating variants (Variant 1 identity-gated for MVP, Variants 2/3 deferred), implementation order (spike → strfry → policy plugin → policy daemon → server.js integration), open questions (key rotation, public-relay defaults, retention policies), and explicit scope-containment ("not a Nostr social network, not a payment channel, not browser-side"). **Read NOSTR-DESIGN-NOTES.md before any v0.19+ Nostr-discovery build session.** The per-user Nostr details below (rate-post fields, NIP-05 endpoint) are complementary, not redundant — both ship together as the v0.18.5+ phased rollout.

#### Locked-in design decisions
- **Per-user Nostr details belong in the rate post**, not in `v4call-server.json`. New optional fields: `NOSTR-PUBKEY: npub1xxx`, `NOSTR-RELAYS: wss://...,wss://...` (optional list), `LIGHTNING-ADDRESS: user@walletofsatoshi.com` (optional). User self-serves via `rate-editor.html`. Operator does nothing per-user. Same trust model as everything else in v4call (Hive identity = source of truth).
- **Server-level Nostr config belongs in `v4call-server.json`**: the operator's own Nostr relay URL (if they run one), the server's own Nostr identity for federation discovery events. Goes through `server-sign.html` + `server-announce.html` like other server config.
- **`/.well-known/nostr.json` is a dynamic server endpoint, NOT a signed static file.** Server reads every local user's rate post and assembles `{"names": {"foo": "abcdef..."}, "relays": {"abcdef...": ["wss://..."]}}` per request. Updates transparently when users update their rate posts. Implements NIP-05 verification.
- **`nostr-gen.html` and `qr-gen.html` already exist** in the repo as standalone tools. Need to be linked from `index.html` / `info.html` so users can find them. `nostr-gen.html` generates the keypair fully client-side; never sends the key anywhere. `qr-gen.html` lets users move secrets between devices via QR scan instead of network transfer.
- **Lightning button is display-only**: v4call infrastructure NEVER touches Lightning Bitcoin. The button just shows the user's Lightning Address (and a QR code + lightning: URL scheme link) so the sender's wallet can pay directly. Recipient gets the funds in their Lightning wallet, no v4call platform fee, no v4call escrow. Pure address-book functionality. Button is **gated on the rate post field being populated** — if `LIGHTNING-ADDRESS` is blank, no button shown.
- **Nostr button works the same way**: display npub, copy button, QR code, optional `nostr:` URL scheme link to open in user's Nostr client. Gated on `NOSTR-PUBKEY` being populated.
- **Hybrid Nostr-aware client (Layer C)** is a far-future option, not a v0.18.5 commitment. Current decision: build display-only first. Re-evaluate hybrid client after seeing real usage of the display-only fields.

#### Phased build path
| Phase | Scope | Estimated sessions |
|---|---|---|
| **v0.18.5 Part A** | Rate-editor extension: `NOSTR-PUBKEY`, `NOSTR-RELAYS`, `LIGHTNING-ADDRESS` fields. Display these on user profiles in v4call (DM panel header, user-list hover). Both buttons gated on rate-post field being populated. Link `nostr-gen.html` + `qr-gen.html` from `index.html` / `info.html`. | 1-2 |
| **v0.18.5 Part B** | Dynamic `/.well-known/nostr.json` endpoint. Server reads local users' rate posts + assembles JSON per request. NIP-05 verification works for `username@v4call-server.com` from any Nostr client. | 1 |
| **v0.18.5 Part C** | Optional verification step in rate-editor: when user adds Lightning Address or NOSTR-PUBKEY, client validates reachability before saving (LNURL endpoint check, Nostr relay roundtrip). Catches typos. | 1 |
| **v0.19** | Nostr-based federation discovery — replace 2h Hive scan with relay subscription for near-realtime peer discovery. Hive announce post stays as auditable record; Nostr is the fast layer on top. Operator runs their own Nostr relay (optional but encouraged). | 2-3 |
| **Far future** | Hybrid Nostr-aware client (Layer C): v4call client filters Nostr DM inbox by "only from accounts on my v4call user-list" or "only with v4call payment proof tag." Cross-network paid DM filter. Complex; defer. | 3-5 |

#### Why this fits v4call
- **Hive payment rail keeps the gate.** Nostr/Lightning don't replace v4call's paid-DM gate; they extend reach without diluting it. The economic chokepoint stays on Hive.
- **Independence-fallback narrative**: if v4call.com is down, users can talk via their Nostr clients using each other's npub (which they got from v4call). v4call becomes a "good citizen" of the wider Nostr ecosystem.
- **No new auth, no new accounts.** Hive identity remains the root. Nostr keypair is supplementary; users who don't want one don't need one.
- **No new infrastructure burden** for v4call operators (Lightning is third-party; Nostr relay is optional; nostr.json endpoint is auto-generated). Operators who want to learn Nostr can run their own relay as a side-quest (this is what the user is doing, plus material for a completenoobs.com walkthrough).

#### SWAP.BTC + Lightning relationship (worth noting)
SWAP.BTC (Hive-Engine wrapped Bitcoin) already works as a v4call payment currency out of the box — confirmed 2026-05-04 testing. Withdrawal back to native Bitcoin via tribaldex has non-trivial fees (minimum 0.01 SWAP.BTC). Lightning Bitcoin is a separate channel (much smaller fees, instant settlement) that v4call surfaces only as a tipping link, not as a paid-gate currency. **A future Hive-side bridge** (Lightning ↔ SWAP.BTC) would let users pay v4call's paid gate in real Bitcoin via Lightning → bridge → SWAP.BTC → v4call rate post accept. Out of scope for v4call code; depends on third-party bridge tooling.

#### Operational notes
- **v4call's own Nostr relay**: operator decision, runs externally to v4call code. Software options: nostream, strfry, etc. The user is planning to run one as a learning project + completenoobs.com walkthrough material. Once running, operator publishes `wss://relay.v4call.com` as part of `v4call-server.json` so other peers know it's available.
- **Public relay choice for clients**: default to a list of well-known public relays (`wss://relay.damus.io`, `wss://nos.lol`, `wss://relay.nostr.band`, etc.). Let users override per-account in their rate post (via `NOSTR-RELAYS` field).
- **Relay filter / ban risk**: some Nostr relays filter content. v4call shouldn't depend on a single relay. Multi-relay redundancy is the standard mitigation.

### v0.19+ → v0.22+ (provisional, phased) — IPFS-backed file attachments
**Big multi-version feature, captured here as a forward-looking plan. Origin: separate brainstorm thread on 2026-05-01. Not blocking v0.17 / v0.18; phased rollout starts after v0.18 spotlight UI overhaul.**

#### The product gap
v4call has no transport for async voice messages, video messages, images, or arbitrary file transfer between users. Current chat envelopes carry text only. Adding async media is a real product gap: live voice/video is already covered by paid calls, but "send me a 30-second voice clip when I'm offline" has no answer today. This plan adds it without compromising the encryption boundary or v4call's payment philosophy.

#### Architecture — locked-in decisions
- **Transport: IPFS** (content-addressed, decentralised, federation-friendly — see "federation natural fit" below). Operator runs their own Kubo node for the hot tier; cold-tier permanent storage delegated to a Filecoin partner (web3.storage / Lighthouse / Filebase / Storacha — DON'T run Filecoin yourself, the deal-making layer is real ops work).
- **Encryption boundary: client-side, end-to-end.** Sender's browser encrypts the file with a fresh AES-GCM key, encrypts that key with each recipient's posting pubkey (same hivecrypt pattern v4call already uses for DMs), signs the ciphertext, uploads ciphertext to IPFS via the operator's pinning proxy. Server only ever sees ciphertext bytes + signature + pubkey + size. No plaintext, no metadata about content, no MIME enforcement.
- **Tags for rendering, not for billing.** Sender includes `<voice>`, `<video>`, `<image>`, `<file>` hint in the envelope so the recipient's client picks the right player. Server cannot verify the tag (would require decryption); pricing must depend only on what the server can measure (size). Tag-based pricing creates an incentive to lie — don't do it.
- **Server proxies all uploads** — `Browser → POST /upload → server.js → Pinata/web3.storage (with secret JWT) → returns CID`. JWT in `.env`, never in browser. Rate-limit the endpoint, validate file size + declared MIME, gate behind signature verification (only registered v4call/Hive accounts can upload).
- **Identity from Hive.** No new auth, no signup flow, no email verification — Hive accounts ARE the identity. Pubkey-signed uploads. Hive `account_update` ops let the server detect key rotations on-chain. Existing v4call rate-post infrastructure extends naturally for accept-rates.
- **Sender pays.** Storage cost (per-byte rate) bills the uploader. Recipient is never charged for receiving — same philosophy as caller-pays-for-receiving in current v4call. This makes the abuse math clean: a malicious user can never DoS another's storage quota.
- **Per-byte pricing** with friendly UI display. Internal: `cost = size_in_bytes × rate_per_byte`. UI: format pro-rata in HBD/HIVE/token. Rate set as "per GB" (human-readable). Floor at 0.001 HIVE per attachment (Hive's smallest unit). Round to 1kb granularity to avoid sub-precision math.
- **Free tier**: per-user storage cap (initially 100MB total, signed by sender's pubkey, server tracks via DB). 7-day TTL (more generous than the 3-day initially considered — some users won't check messages for a week). Server cron unpins after TTL, runs `ipfs repo gc`, decrements quota.
- **Paid tier**: above-quota uploads bill per-byte from sender's escrow (HBD or token, whatever the recipient accepts). Permanent or extended TTL via Filecoin cold-tier partner.
- **Federation natural fit**: when @foo on call.completenoobs.com sends a voice note to @bar on hive-book.com, foo's server pins the encrypted blob → forwards a federation `dm` envelope with `attachments: [{ cid, mime, size, encKey, sig }]` → bar's client fetches the CID from any IPFS gateway (foo's, bar's, ipfs.io, Cloudflare's). **No cross-server pin replication needed** — IPFS is content-addressed; any gateway resolves any CID. The encryption is end-to-end so no gateway can read the bytes. This is the cleanest fit for cross-server async media transfer; the alternative (S3-style server-to-server file exchange) would require API keys, signed URLs, and a lot more federation-protocol surface.
- **Recipient size cap** (new rate-post field `ATTACHMENT-MAX-MB`). Server validates blob size against recipient's declared accept-limit before forwarding the federation envelope. Without this, a malicious sender could fund a 50GB attachment that the recipient doesn't want; with it, recipient declines-by-default for oversized files.

#### Phased build path
Each phase is independently shippable. Don't build phase N+1 until phase N is in production and people are using it.

| Phase | Scope | Estimated sessions |
|---|---|---|
| **v0.19** | Voice messages in DMs only. Single pinning provider (Pinata or web3.storage). Free 100MB/user, 7-day TTL, fixed simple rate. No rooms, no Filecoin, no pool. "Press to record → encrypt → upload → CID in DM envelope → recipient plays inline." Validates the whole crypto + IPFS flow with minimal moving parts. | 2-3 |
| **v0.20** | Video + image + arbitrary file in DMs. Same plumbing, more MIME types. Per-byte recipient rates via rate-post extension (`FILE-TRANSFER` field). Recipient `ATTACHMENT-MAX-MB` accept-limit enforcement. | 2 |
| **v0.21** | Paid rooms unlock IPFS attachments (sender-pays from own quota). No room treasury yet — just "this room allows attachments, billed to sender per-byte same as DMs." | 2 |
| **v0.22** | Pool accounts + time-based room billing. Virtual ledger. Server-as-escrow with admin-set fee % (fee on consumption, not gross deposits). Pro-rata refund on close (Model A first; Model B as room-creator option later). Buffer mechanic before shutdown (default 3 hours, creator-configurable, progressive notifications at 50%/75%/final). | 4-5 |
| **v0.23+** | Filecoin cold tier for permanent storage. Partner integration (web3.storage / Lighthouse / etc.). Opt-in "keep forever" with explicit pricing. Cold-tier latency caveat surfaced in UI. | 2-3 |

#### Spam control (stacked)
1. **Sig check at upload** — only registered Hive accounts (verified pubkey) can upload. Stops random strangers entirely.
2. **Per-user storage quota** — 100MB free tier cap. A compromised account is a 100MB problem, not unbounded.
3. **Recipient-side gates** — existing v4call rate-card (per-byte rate, ATTACHMENT-MAX-MB cap, blocked-list, ALLOW-IF-TOKEN bypass). Stops the social spam problem.
4. **Hive economic backstop** — paid attachments require on-chain payment, so spammers pay real money per spam. Already baked into v4call's rate model; extends for free.

#### Server-as-escrow (when v0.22 lands)
Single Hive escrow account holds all room treasuries in aggregate. Internal DB tracks virtual balances per room, per contributor. Server takes admin-set fee on consumption (NOT on gross deposits — refunds untouched on unused rooms builds trust). Active key on server, owner key offline. Daily transfer caps, reconciliation alerts, 10% reserve buffer. **Make a note for later: at growth scale this becomes a regulatory + key-security concern; might want multisig or per-user escrow accounts when scale demands.** Not a v0.22 issue.

#### Operational hard parts to plan for
- **iOS Safari MediaRecorder pain** — `audio/webm` doesn't work on iOS Safari/Brave (WebKit). Need `audio/mp4` recording fallback OR server-side transcode. Test on iPhone EARLY, before building features on top. Same trap that bit v0.16 mid-room-cam-toggle.
- **Filecoin retrieval latency** — first-byte from cold tier can be 30 seconds to several minutes. Don't auto-promote to cold unless user pays for permanent. Surface latency caveat in UI when user requests "keep forever."
- **Key rotation** — undelivered messages encrypted to old keys are stuck if recipient rotated owner key. Include `recipient_key_fingerprint` in the attachment envelope so client can flag "encrypted to a key you no longer hold" instead of silent decryption failure. v4call's existing chat already has this problem; piggyback on the existing handling.
- **Don't underestimate policy/UX work** — pricing UX, quota visualisation, buffer notifications subsystem (don't have one yet), refund mechanics, transparent fee disclosure, ToS updates. Plan for as long as the code work — maybe longer.

#### Forward-compat with current architecture
- **Rate post extension is non-breaking**: new fields `FILE-TRANSFER: 1.0 HBD/GB` and `ATTACHMENT-MAX-MB: 100` slot into V2 / V3 rate post format. Existing parsers ignore unknown fields gracefully (V1/V2 backwards-compat is already how v4call handles rate-format evolution).
- **`computePaymentOptions` helper extends naturally** — already returns multi-currency options. Add a `fileTransfer` field to each option (rate per GB, max attachment size). Same pattern as the v0.16.6 multi-currency fix.
- **Federation `dm` envelope** — already carries arbitrary fields. Add `attachments: []` array. v0.4 peers without v0.5+ won't know to look for `attachments` and will deliver a normal DM (just without the file); v0.5+ peers fetch via IPFS gateway and render. **No federation protocol bump needed for v0.19 (DM-only attachments)**; the bump would be needed when paid rooms unlock attachments (v0.21+) since that introduces new payment flows that need cross-server validation.

#### Why this fits v4call
- v4call is decentralised; central server stores ciphertext but never plaintext. IPFS extends this to file content — naturally on-brand.
- Hive payment rails already cover the economic flows (no Stripe, no card processor, no chargebacks).
- Existing rate-post infrastructure already covers "what does this user accept and at what cost."
- Existing `.v4room` export pattern (v0.14.5) is a good template — client-side-encrypted bundle, addressable by content. The CID is just a more decentralised version of "filename + bytes."

### Deferred / On Hold
- **Paid lobby posting** (charge per message in lobby) — interesting but operational complexity > value at this stage
- **Paid room creation** (charge fee to create a room) — same reasoning
- **Split-equal expert pay** (v0.17 extension) — N members pre-fund their share before the invite goes out; invite holds until everyone's funded. More coordination friction; defer until single-payer is proven and there's demand.
- **Pay-as-you-add expert pay** (v0.17 extension) — admin invites the expert, individual members opt in to sponsor a share. Most complex of the three payer models; defer.
- **Connect fee charged upfront on accept** (v0.17 toggle) — opposite of the locked-in "bundle with final bill" mode. Some admins may prefer it; add as a per-invite toggle if requested.

### Longer-Term Future Work
- **HiveSigner as an alternative to Hive Keychain** (login + paid actions). Currently v4call supports two login paths: Keychain extension (recommended) or manual posting-key paste. Add HiveSigner as a third option — especially valuable on mobile. Two parts:
  - **Part A — HiveSigner login**: OAuth-style flow. User clicks "Sign in with HiveSigner" → redirected to `https://hivesigner.com/oauth2/authorize?...` → user approves → returns to v4call with an access token. v4call uses the token to verify identity and fetches the user's posting pubkey from Hive (no private key ever in v4call's hands). Same security posture as Keychain login, just a different user-facing flow.
  - **Part B — HiveSigner paid actions**: For Hive transfers (HBD/HIVE) use `https://hivesigner.com/sign/transfer?...`. For custom JSON ops (Hive-Engine token transfers) use `https://hivesigner.com/sign/custom-json?...`. User approves the action in a HiveSigner tab and returns to v4call. Adds an external dependency (hivesigner.com uptime + trust) but works with no extension on any device including iOS. Bigger fancier version uses `@hiveio/keychain-sdk` (QR/deep-link to the Keychain mobile app) but requires a build step (npm). HiveSigner web flow stays simpler and dependency-free.
  - **Why important**: iOS Safari + iOS Brave don't allow the Keychain extension to inject `window.hive_keychain`, so paid actions on iPhone currently fail. HiveSigner is the workaround. Also: many casual users find OAuth flows less intimidating than installing a browser extension. Lowers the friction-to-first-call.
- Persistent (non-ephemeral) rooms option
- Per-conversation read tracking (currently per-user last_seen)
- Voice-to-video upgrade mid-call (now half-built — v0.12 added enable-mic / enable-cam mid-room with renegotiation; the 1:1-call upgrade variant would reuse the same mechanism)
- STUN/TURN server configuration via .env

- Input validation hardening
