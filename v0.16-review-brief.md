## What v4call is (one paragraph)

Decentralised paid video/voice/text comms on the Hive blockchain. Callers pay HBD or custom Hive-Engine tokens to ring callees; users set their own rates; unused credit refunds. Servers federate so users on different domains can call/DM/share-rooms. Backend is Node.js + Socket.io + better-sqlite3 + ws (federation WebSocket); frontend is a single `public/index.html` (intentional). Client-to-client media is WebRTC P2P. Federation is server-to-server WebSocket on `/federation` with a Hive-key-signed `/.well-known/v4call-server.json` for domain proof.

## Project constraints (these matter for your review)

1. **Single-file frontend** — every UI change goes into `public/index.html`. Do not suggest splitting it into modules. There are four standalone operator tool pages (rate-editor, server-sign, server-announce, admin-peers, info) — they're allowed to stay separate.
2. **No new npm dependencies** unless absolutely necessary.
3. **No comments explaining WHAT code does** — only WHY-comments when the reasoning is non-obvious.
4. **No backwards-compat shims, no half-finished implementations, no over-engineered abstractions** — three similar lines is better than a premature abstraction.
5. **Federation backwards-compat is non-negotiable.** A v0.3 peer must continue to federate fully with a v0.4 peer for everything they could do at v0.3 (DMs, 1:1 calls, presence, payments). v0.4-only features (cross-server room invites + room joining) are gated by the `protocol_version` field in the federation hello envelope.
6. **`.shown` class pattern for hidden-by-default buttons.** Setting `style.display = ''` does NOT override CSS `display: none` (the cascade re-applies). Use `#id { display: none; } #id.shown { display: inline-block; }` and `classList.toggle('shown', cond)`.
7. **Hive `condenser_api.get_discussions_by_*` `limit` cap is 20.** Higher values silently fail with `Assert Exception`.
8. **WebRTC SDP m-lines bug** — text-only / voice-only joiners need `pc.addTransceiver(kind, { direction: 'recvonly' })` for the kinds they're not sending, otherwise the offer SDP has zero `m=` lines and the answer mirrors that → existing peers' tracks are attached but never sent.

## What v0.16 ships

### Part A (shipped earlier)
- Federated room invites — admin types `@user@peer.com` into a room's allowlist; server sends `room-invite` over federation; receiving server delivers a popup with source-server badge; accept/decline flows back as `room-response`.
- New federation envelopes: `room-invite`, `room-response`. Both validated against `peerSupportsV04()` and approved-peer set.
- `protocol_version: '0.4'` field added to the federation hello envelope. Old peers ignore it, new peers gate v0.4-only features on it.
- `pendingFederatedInvites` map with 15-minute TTL sweep.
- Forward-compat: `room-invite` envelope has a generic `payload: {}` field so v0.17 (Paid Expert Invites) can populate it without inventing a new message type.

### A.5 polish
- Invite-flow system messages (`📨 Invite sent`, `✓ accepted`, `⚠ offline`, `⚠ Allowlist: ...`) route to the user's current room when they're in one (lobby gets busy with broadcast traffic; admin in a room couldn't see them).
- `room-create` resolves federated invitees: explicit `user@server` form OR bare username + `peerForUser()` fallback (so lobby user-picker selections of federated users actually invite).

### Part B (cross-server room join)
- `socket.on('join')` accepts a `homeServer` field. Federated joiners match canonical `${username}@${homeServer}` against the allowlist; tokenGate balance check uses bare username (chain-side, peer-agnostic).
- Room-state payloads (`room-users`, `room-users-resync`, `user-joined`) thread `homeServer` so client can render a server badge in the user-list and on video tile labels.
- Federated badge rendering mirrors the existing lobby + allowlist styles.
- Federation peer drop while a federated user is mid-room → `cleanupFederatedMembersForPeer(domain)` evicts them immediately (per design choice — rooms have no payment to refund).
- Member dedup uses canonical key so local `@noblemage` and federated `@noblemage@hive-book.com` can coexist.

### B.5 / B.6 hotfixes
- B.5: Allowlist match in the join handler now tries canonical first, falls back to bare for federated joiners. Without this, federated 1:1 calls broke because call rooms have bare-name allowlists.
- B.5: Temp-socket disconnect handler gates on `reason === 'io server disconnect'` only. Without this, transient transport blips were calling `leaveRoom()` and yanking the user out of an active call.
- B.6: 1:1 call rooms now initialise `banlist: new Set()`, `tokenGate: null`, `banlistVisibility: 'admin'`, `paidInvitees: new Map()`, `spotlight: null` at creation. Without these, Part B's broader field expectations crashed the Node process whenever anyone joined a call room.

## Known bugs / concerns the author would like fresh eyes on

**A. Cam/mic/screen-share reliability.**
The author reports cam/mic/screen-share working sometimes and breaking other times in cross-server rooms after Part B shipped. The B.6 server-crash fix (above) plausibly explains most of the symptoms (server was crash-looping every time anyone joined a call room, which was happening constantly during testing). But it's worth a fresh look at:
- The temp-socket reconnect path — when the temp Socket.io reconnects after a transient drop, does the user need to re-emit `join` to be re-bound to the room on the host server?
- The disable→re-enable cam path — author reports cam works initially but doesn't recover after disable/re-enable in some cross-server cases.
- The screen-share `replaceTrack` vs `addTrack + renegotiate` paths in `toggleScreen()` / `startScreenShare()` / `stopScreenShare()`.

**B. WebRTC pairing with mixed local + federated members in the same room.**
Three or more participants where one is on a different home server. WebRTC offers/answers all relay through the host server (which is in the middle for media signalling, not media itself). Are there any pairing edge cases where two federated peers in the same room (each on a different home server) won't establish a P2P connection?

**C. Username spoofing / temp socket auth.**
The temp Socket.io connection from a federated joiner to the host server doesn't have any cross-server identity verification — it just sends `{ username, pubKey, homeServer }` and the server trusts it (subject to the allowlist match). This is the same trust assumption the existing 1:1 federated calls already make. Documented in CLAUDE.md as known security limitation. Worth flagging if there's a tighter pattern that doesn't add federation-side complexity.

**D. Federation hello backwards-compat audit.**
v0.4 added `protocol_version: '0.4'` to the hello envelope. Old v0.3 peers shouldn't read it (they don't), but please confirm by reading `fedHandleMessage`'s `case 'hello':` block that nothing v0.4-specific would crash a v0.3 peer.

**E. Socket.io self-skip in `applyRoomUsers`.**
The function used to skip self via `u.socketId === socket.id`. This breaks for federated joiners because the host server's socketId for the temp socket is different from the joiner's main `socket.id`. Part B changed it to `u.username === myUsername`. Please confirm this doesn't introduce any regression in the local-1:1-call or local-multiparty-room paths (where the old check worked).

**F. Memory hygiene.**
- `pendingFederatedInvites` has a 15-minute TTL sweep. Are there any other Maps or Objects in `server.js` that grow without bound and could leak memory?
- `dmHistoryLoaded` (client-side `Set`) used to dedup DM previews per session. Is it cleared on logout/reconnect?

**G. Race conditions on room state mutations.**
`r.members` is mutated from many places (join, leave, disconnect, ban, federation-drop cleanup, room-end-all). All of these run on the same Node event loop, so there's no actual concurrent write — but the ORDER of state mutations matters. Are there any code paths where, e.g., `r.members` is iterated AFTER a mutation that should have invalidated the iteration?

**H. The `bare-fallback` in the allowlist match.**
B.5's fix for federated 1:1 calls added: `else if (isFed && r.allowlist.has(username)) joinedVia = 'allowlist';`. Concern: if a v0.16 federated room has a SECOND allowlist entry that happens to be a bare local username matching a federated joiner's bare name (e.g. allowlist has `noblemage` and `reeman@v4call.com`, and `reeman@hive-book.com` from a different server arrives), would `reeman@hive-book.com` match the bare `noblemage`? No (different bare name). But what about: allowlist has `noblemage` (bare local) and `noblemage@hive-book.com` (federated). A federated `noblemage@third-server.com` arrives — would they match the bare-fallback against `noblemage`? With `r.allowlist.has('noblemage')` → TRUE → joined as `allowlist`. That's a security concern. Worth a closer look at whether this fallback should be restricted to only `r.isCall === true` rooms.

**I. Comment hygiene.**
The author's coding style is "no comments explaining what code does, only why when non-obvious." Please flag any new comments I added that explain the WHAT rather than the WHY — they should be removed.
