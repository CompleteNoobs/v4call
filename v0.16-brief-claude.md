## Where we are

- **v0.15 is shipped + production-deployed** on call.completenoobs.com ↔ hive-book.com. Spotlight room layout, local pin, admin spotlight broadcast (soft override + ↺ Follow room spotlight), admin role transfer (👑), Share Screen wired up, plus the WebRTC SDP m-line fix that lets text-only / voice-only joiners actually receive existing peers' video and audio.
- **Federation protocol still at v0.3** — unchanged since v0.11. v0.16 is the **first federation bump since v0.11**, taking the wire format to **v0.4**.
- **1:1 cross-server calls already work** at the v0.3 wire level. The pattern v0.16 extends: caller's server hosts the room, callee's browser opens a temporary cross-server Socket.io connection for WebRTC signalling, media stays peer-to-peer. Cross-server payments work too (caller pays callee's escrow on Hive directly; callee's server disburses).

## Hard constraints (already in CLAUDE.md but reinforced here)

1. **Single-file frontend** — every change goes into `public/index.html`. Don't split.
2. **No new npm dependencies, no Dockerfile changes.**
3. **CSS variables only.** Dark theme. IBM Plex Mono / Sans.
4. **No comments explaining what code does** — only why-comments when non-obvious.
5. **`.shown` class pattern for hidden-by-default buttons.** Never `style.display = ''` (see Known Gotchas in CLAUDE.md).
6. **Federation backwards-compatibility is non-negotiable.** A v0.3 peer must still be able to handshake with a v0.4 peer and use all the features they had at v0.3. v0.4 just adds new message types — old peers ignore unknowns; new features only activate when both ends are v0.4+.
7. **Forward-compatibility for v0.17 (Paid Expert Invites).** Per CLAUDE.md: design `room-invite` as a generic envelope with a free-form `payload` object rather than fixed fields. v0.17 will reuse this with `payload: { connectFee, ratePerHour, currency, maxDuration, ... }` instead of inventing a separate `paid-room-invite` message type. Cross-server room-join flow should track an optional per-user "billing context" (null in v0.16 for free invitees, an `activePayments` reference for paid invitees in v0.17).
8. **Hive `condenser_api.get_discussions_by_*` `limit` cap is 20.** Not relevant here but stated for completeness.

## What v0.16 ships — two independent parts

Both parts target the **same** end-to-end feature: a user on `call.completenoobs.com` invites `@reeman@hive-book.com` to a room on call.completenoobs.com, reeman accepts, joins the room, sees other members (including federated ones), token-gating works for non-allowlisted joiners. Each part is shippable independently — Part A gives you the invite/accept handshake without the actual cross-server presence; Part B turns it into a real working room.

### Part A — Federated room invite + accept/decline (1 session) — start here

**Today:** Admin can invite a *local* user via the existing `room-invite` socket flow. There's no cross-server invite mechanism for rooms (1:1 calls work because the call flow has its own cross-server message types).

**v0.16:** Admin creates a room and invites a federated user (e.g. via the allowlist UI accepting `@cnoobz@hive-book.com` syntax, or via a new "Invite federated user" affordance). The invite flows through the federation socket to the callee's home server, which delivers it as a popup the same way local invites land. The callee accepts/declines; the response flows back.

**New federation message types (wire format = v0.4 additions):**

- `room-invite` — generic envelope: `{ type: 'room-invite', invite_id, from_user, to_user, room_name, source_server, payload: {} }`. The empty `payload` is the v0.17 hook — paid invites populate it; v0.16 leaves it empty.
- `room-response` — `{ type: 'room-response', invite_id, response: 'accepted' | 'declined', reason? }`.

**Server-side (caller's server — the one hosting the room):**
- New socket handler `room-invite-federated` (or extend the existing `allowlist-add` to detect federated targets). When admin invites `cnoobz@hive-book.com`:
  - Validate target's home server is an approved federation peer.
  - Add `cnoobz@hive-book.com` to the room's allowlist (decide canonical form below — see questions to ASK).
  - Generate `invite_id`, send `room-invite` over federation socket to peer.
  - Track pending invite in memory: `pendingFederatedInvites[invite_id] = { room, from_user, to_user, source_server, expires_at }`.

**Server-side (callee's home server — the one delivering the popup):**
- New federation message handler for `room-invite`. Verify peer is approved. Look up `to_user` in `lobbyUsers`. If online, emit `room-invite` socket event to that user (matching the existing local invite payload shape so the client UI is unchanged). If offline, optionally store as a pending invite (or just decline-with-reason — decide).

**Client-side:**
- Existing `room-invite` socket event already shows the popup. Server-side delivery just needs to make the federated invite look identical (with an extra `from_server` field). Client adds a small `@source.com` badge in the popup so the user knows it's federated.
- Accept → emit `room-accept-federated` (or reuse existing `acceptInvite` with a federation flag). Server sends `room-response` back over federation. Caller's server gets the response, marks the invite resolved, broadcasts updated `room-info`.
- Decline → same flow with `response: 'declined'`.

**Federation v0.4 hello bump:** add `protocol_version: '0.4'` to the federation hello payload. Existing v0.3 peers won't read it (and won't send it back). v0.4 peers send + read it. We use this to **gate v0.4-only features**: don't send `room-invite` over federation to a v0.3 peer (silently no-op or surface "peer not on v0.4+ yet" client message).

### Part B — Cross-server room join (multi-party WebRTC + token-gate) (1 session)

**Today:** When reeman accepts the federated invite from Part A, there's no actual mechanism for them to join the room. Part A's accept-flow needs Part B to be useful end-to-end.

**v0.16:** Reeman's browser opens a temporary cross-server Socket.io connection to call.completenoobs.com (the room's home server), the same way 1:1 federated calls already do. The temp connection joins the room, sees all members, exchanges WebRTC offers/answers with everyone (including the spotlight pin from v0.15), and chat messages flow as normal.

**Approach (mirror the existing 1:1 federated call flow as closely as possible):**
- The 1:1 federated call already has working code for the temp cross-server Socket.io (search `activeRoomSocket` in `public/index.html`). Reuse that machinery for room joins.
- Server-side: existing `socket.on('join', ...)` handler should mostly Just Work — the cross-server socket joins as if it were a local user. The catches:
  - Username uniqueness across federation: a member joining from `@cnoobz@hive-book.com` shouldn't collide with a local `@cnoobz`. Decide canonical form (see questions to ASK).
  - The `join-rejected` paths (banlist, allowlist, tokenGate) need the same cross-server semantics. The `username` argument needs to match what the server stored on the allowlist.
  - For token-gating: `getHiveEngineTokenBalance(username, symbol)` is **chain-side** — works the same regardless of which server the user is on. So token-gating across federation is essentially free, just need to make sure we use the bare username (not `username@server`) for the chain query.

**Federation `room-ended` message:** when a room is destroyed (last member leaves, admin clicks End Room) or a federated member is kicked (banned), the caller's server should notify peer servers so they can clear local state for that user (remove from `inRoom` lobby field, etc.).

**WebRTC across federation:** P2P media still works exactly as before — the temp cross-server socket just relays signalling. The `createPC` / `pc.ontrack` flow from v0.15 is peer-agnostic.

**Spotlight broadcast across federation:** v0.15's `room-spotlight-changed` event is local-only today (all members on the same server). With v0.16's cross-server members on the same room, the same `io.to(room).emit(...)` should reach everyone since the temp cross-server socket has joined the Socket.io room. Verify this works without changes; if not, route via federation explicitly.

## Style references (already-working patterns to copy)

- **1:1 cross-server calls — the existing pattern to mirror.** Search `activeRoomSocket` in `public/index.html`. The temp Socket.io connection that opens to the caller's server when reeman accepts a federated 1:1 call is the model for room joins. Same lifecycle: open on accept, close on leave.
- **Federation message dispatch.** In `server.js`, the federation WebSocket handler dispatches by `msg.type`. Add new types alongside the existing `dm`, `call-invite`, `call-response`, `payment-verified`, etc. Each handler should re-verify the peer is approved before acting.
- **Per-socket message ordering.** Each federation WebSocket has a Promise queue chain (per CLAUDE.md design decision #11). New message handlers must respect this — don't break ordering by spawning unawaited promises.
- **Room state mutations always go through `emitRoomInfoToMembers(r, roomName)`.** Used by allowlist-add/remove, ban/unban, role transfer, spotlight broadcast (v0.15). When a federated invite is accepted and the new member joins, they get `room-info` via the normal `socket.emit('room-info', ...)` in the join handler.
- **Federation backwards-compat sniff via the hello.** The existing federation hello already exchanges `escrow_account`. Adding `protocol_version: '0.4'` is the same pattern. Read it back in `federationPeers[domain].protocolVersion` and gate v0.4 features on it.

## Things to ASK the user about before each part starts

For each part, before generating any code, ask:

### Before Part A
1. **Allowlist canonical form for federated users.** Should the room's allowlist store `cnoobz@hive-book.com` (with server suffix), or just `cnoobz` (bare)? Tradeoff: storing the suffix protects against username collisions across federation, but breaks the assumption everywhere else in the codebase that allowlist members are bare usernames. Recommendation: store the suffix for federated entries (`username@server`), and update the join check to compare both forms.
2. **Inviting a federated user — UX surface.** Today the allowlist add input takes a bare `@username`. For v0.16, should typing `@cnoobz@hive-book.com` Just Work in the same input (auto-detected as federated)? Or add a separate "Invite federated user" button? Recommendation: same input, auto-detect — fewer UI surfaces.
3. **Decline invite — silent or notify?** When reeman declines, should cnoobs see a `@reeman declined your invite` system message in the room, or silent (matches today's local-invite decline behavior — check first)? Recommendation: match local behavior exactly.

### Before Part B
4. **Username display when federated.** In the room user-list and on video tiles, should reeman show as `@reeman` or `@reeman@hive-book.com`? Today the lobby federated user list shows the badge separately. Recommendation: bare `@reeman` + small `@hive-book.com` badge, mirroring lobby.
5. **Federation drop while in room.** If the federation connection between call.completenoobs.com and hive-book.com drops while reeman is in the room: (a) immediately remove reeman from the room (and let them rejoin when federation reconnects), or (b) grace period (e.g. 30s — same as call-disconnect grace) before removing? Recommendation: (a) immediate — rooms are different from calls (no payment to refund), and Socket.io's own reconnect handles brief blips at the temp-socket layer anyway.
6. **Token-gate username form for the chain check.** When checking `getHiveEngineTokenBalance(username, symbol)` for a federated joiner, use bare `cnoobz` (Hive identity is server-agnostic). Confirm — this should be obvious but flag any edge case I'm missing.

These are real design choices the user should make, not defaults you should pick silently.

## Why this version matters

v0.16 is the second time the federation protocol bumps (first was v0.11 → v0.3 baseline). Until v0.16, every paid v4call interaction is **1:1**. v0.16 unlocks **multi-party** across federation — rooms become the cross-server primitive. That's the foundation for v0.17 (paid expert invites turn rooms into paid consulting calls), v0.18+ (whatever next), and any future "spaces" / "channels" / persistent-room features.

Get the wire format right and forward-compatible (the `payload` envelope) — future versions add features without ever needing another v0.5 / v0.6 / v0.7 wire bump.
