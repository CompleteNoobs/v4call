## What v0.15 ships — three independent parts

### Part A — Spotlight Room Layout (1 session) — start here

**Today:** `#video-panel` is a vertical column on the left of the chat. Local-video is the first `.video-wrapper`; peer tiles get appended below. Equal-sized tiles get cramped fast as people enable cam.

**v0.15:** One large **spotlight** tile + smaller peer tiles arranged below it (or in a horizontal strip across the top).

**Approach (recommended — simplest diff):**
- Convert `#video-panel` to CSS grid: `grid-template-rows: 1fr auto;` (spotlight row takes remaining space, peer-strip row sits below).
- Add a `.spotlight` class. The tile with this class lives in row 1, fills the panel. All other `.video-wrapper` tiles live in row 2 as a horizontal flex strip with smaller fixed width (~120px).
- On room entry, the local tile gets `.spotlight` by default.
- A new client function `setSpotlight(socketId)` removes `.spotlight` from the current tile and adds it to the chosen one. Used by Part B.
- **No active-speaker auto-detection in v0.15** — only manual click-to-promote (Part B) controls who's in the spotlight. Auto-detect via `getSynchronizationSources()` audio levels can be a v0.16 add-on.

**Make the strip clickable:** add `onclick` to each peer tile so clicking it pins them to spotlight (preview of Part B's admin-promote behaviour for non-admin users — they can locally pin anyone to *their own* view, but server doesn't change for other members).

Wait — actually keep client-side pinning admin-only. Otherwise it's confusing when "click to spotlight" means different things for different roles. Decide: either (a) admin-only click-to-promote (broadcast to room — Part B work) OR (b) anyone can pin locally to their own view. Pick one. **Recommend (b) for Part A** since it gives every user agency over their own layout, and (a) becomes "admin enforces a default for the room" in Part B.

**Mobile:** the room screen on mobile already has a bottom-tab nav (`VIDEO / CHAT / MEMBERS`). Spotlight layout on mobile = spotlight tile fills viewport, peer strip horizontally scrolls below. CSS at `@media (max-width: 720px)` already has `#video-panel` adjustments — extend them.

### Part B — Admin Click-to-Promote + Role Transfer (1 session)

Two new server events, two new client UIs:

**Click-to-promote (room-wide):**
- Admin clicks a member in user-list or peer tile → client emits `room-spotlight-set` with target socketId or username.
- Server validates `socket._username === r.creator`, broadcasts `spotlight-changed` with target socketId to all room members.
- All clients call `setSpotlight(targetSocketId)` (the function from Part A).
- Persist the spotlight target on `rooms[room].spotlight = socketId` so users joining later see the right person.

**Admin role transfer:**
- Add a "Make Admin" button next to each member in the admin's allowlist panel.
- Click → confirms ("Hand admin to @username? You'll lose admin powers and they'll gain them.") → emits `room-transfer-admin` with target username.
- Server validates current admin, sets `r.creator = newAdminUsername`, calls `emitRoomInfoToMembers(r, room)` so every client gets fresh creator field.
- Client `room-info` handler already updates `amCreator = (creator === myUsername)` — that machinery handles the visibility flip of admin-only UI (End Room, ban controls, transfer button) automatically.
- Edge case: target must be a current member (not just allowlisted-but-not-in-room). Reject otherwise with a clear message.

### Part C — Wire up the 🖥️ Share Screen button (1 session)

The button has been a placeholder since v0.13. Wire it to `navigator.mediaDevices.getDisplayMedia()`:

**Toggle behaviour:**
- Initial state: button reads `🖥️ Share Screen`.
- Click → `getDisplayMedia({video: true})` → if user grants, swap into the video sender via `RTCRtpSender.replaceTrack()` (no full WebRTC renegotiation needed — replaceTrack is in-place).
- Mutually exclusive with cam — if cam is on when share starts, stop the cam track first and replace its sender with the screen track.
- Once sharing, button text becomes `🖥️ Stop Sharing`.
- Click again → stop the screen track, restore button text. If cam was on before sharing, optionally restore it (or leave video off — your call, **suggest leave-off for simplicity**).

**Browser-initiated stop:**
- The browser shows a "Stop sharing" floating bar when `getDisplayMedia` is active. Clicking that ends the track without going through our button.
- Listen for `screenTrack.onended` → run the same cleanup as the button-click stop. Without this, our button label gets out of sync.

**iOS / mobile capability:**
- iOS Safari/Brave doesn't support `getDisplayMedia`. Detect via `if (!navigator.mediaDevices.getDisplayMedia)`.
- Either hide the button entirely on iOS, or show a clear `Screen sharing not supported on this device` system message when clicked. Recommend the message — keeps the UI consistent across devices.

**Spotlight integration (if Part A is shipped first):**
- When share starts, auto-promote the sharer to the spotlight (calls Part B's broadcast or just locally — admin can override).
- When share stops, leave spotlight as-is unless the sharer was *only* in the spotlight because of the share.

## Test plan template (apply to each part)

After each Part ships and the user rebuilds:

### Part A — Spotlight layout
1. Multi-party room with 3+ members. Each enables cam at different times.
2. Local tile starts in spotlight. Peer tiles appear in the strip below, smaller.
3. Click a peer tile → spotlight swaps to that peer (locally if Part B not shipped; room-wide if it is).
4. Disable everyone's cam → tiles go empty / panel stays sensible.
5. Mobile (iPhone Brave + Linux Brave): spotlight fills the viewport, strip scrolls horizontally.

### Part B — Admin promote + transfer
1. Admin sees "Make Admin" button next to each allowlisted member in admin panel. Non-admin members don't.
2. Admin clicks a member → confirm → that member is now admin (their UI now shows admin buttons). Original admin is now a regular member.
3. Admin clicks a member's tile → server-side spotlight target updates → ALL clients see that member in the spotlight.
4. New member joining mid-session sees the current spotlight target correctly (server emits initial state).

### Part C — Screen share
1. In a room, click `🖥️ Share Screen` → browser permission prompt → choose a screen/window/tab → screen appears in your local tile and all peers see it.
2. Button text changes to `🖥️ Stop Sharing`.
3. Click button again → stops, returns to text/cam state.
4. Use the browser's own "Stop sharing" floating bar → button correctly resets to `🖥️ Share Screen` (the `onended` listener fired).
5. On iOS — clicking the button shows the "not supported" system message; no crash.
6. Cam interaction: cam on, click Share Screen → cam stops, screen appears. Stop Share → video off (or restored — match what was implemented).

## Style references (already-working patterns to copy)

- **Hidden-by-default buttons → use `.shown` class pattern.** See `#enable-mic-btn` in `public/index.html` (and the bug story in CLAUDE.md Known Gotchas — never use `style.display = ''`).
- **Mid-room media changes use renegotiation via `createOffer` / `setLocalDescription` / `rsock().emit('offer')`.** See `enableMic` / `enableCam` in `public/index.html`. Screen share uses `replaceTrack` instead (in-place, no renegotiation).
- **Server-side admin checks: `socket._username === r.creator`.** See `room-ban`, `room-unban`, `room-end-all` for the pattern.
- **Admin-only UI gating:** `if (amCreator) ...` on the client. The `room-info` handler updates `amCreator` and shows/hides admin controls accordingly — Part B's role transfer relies on this for the new admin to instantly get admin UI.
- **Per-recipient socket events: `emitRoomInfoToMembers(r, roomName)`.** Use this when banlist visibility differs per recipient. For broadcast events (spotlight changes, admin transfers), `io.to(room).emit(...)` is fine.

## Things to ASK the user about before each part starts

For each part, before generating any code, ask:

- **Part A:** "For the click-to-spotlight behaviour, should clicking a peer tile change the spotlight just for *me* (local pin) or for the *whole room* (broadcast)? If whole-room, that's Part B work — I'd recommend local-only for Part A and admin-only-broadcast in Part B."
- **Part B:** "Should the admin-promote button appear (a) on each peer's video tile (click the tile to promote), or (b) only as a button in the admin panel next to allowlist names? Or both?"
- **Part C:** "When user clicks Stop Sharing, should the cam they had on before share-start be restored automatically, or should video stay off until they manually click Enable Cam?"

These three questions are real design choices the user should make, not defaults you should pick silently.
