## Hard constraints (already in CLAUDE.md, restated for emphasis)

1. **Single-file frontend** — every change goes into `public/index.html`. Don't split.
2. **No new npm dependencies, no Dockerfile changes.**
3. **CSS variables only.** Dark theme. IBM Plex Mono / Sans.
4. **No comments explaining what code does** — only why-comments when non-obvious.
5. **`.shown` class pattern for hidden-by-default buttons.** Never `style.display = ''`.
6. **Federation backwards-compat is non-negotiable.** v0.4 peers must still federate fully with v0.5 peers for everything they could do at v0.4. v0.5-only features (paid expert invites carrying a non-empty `payload`) gate on a new `protocol_version: '0.5'` hello field — same pattern as v0.4 → v0.3.
7. **Use the existing `payload: {}` hook in the `room-invite` envelope.** Do NOT invent a separate `paid-room-invite` envelope. v0.17 fills `payload`; that's it.
8. **Recipient-side enforcement principle (Key Design Decisions #15)** applies to v0.17 too. Even though the inviter holds the funds, the expert's home server should still validate the offer terms are sensible before the expert auto-accepts.

## Pre-build questions to ASK the user before each part

These are real design choices, not defaults to pick silently.

### Before Part A

1. **Offer-builder UX surface.** Two options: (a) new 💎 button alongside the existing 📌 (spotlight) and 👑 (admin transfer) per-row buttons in the room user-list; clicking on a non-paid user pre-selects them in the offer-builder. (b) Standalone 💎 button in the room toolbar opens a modal with a user picker. Recommendation: (a) — fewer modals, more discoverable, mirrors how spotlight/admin-transfer work.
2. **Settlement model confirmation.** Locked-in design: each offer is its own contract; if the expert disconnects, that contract settles for elapsed time. Re-invite = fresh offer (admin can set a new connect fee or 0). No "waive on re-invite" toggle. Confirm this still holds.
3. **Multiple paid experts in one room.** v0.17 first build: **one paid offer at a time per inviter** (locked-in simplification). Confirm this — expanding to multiple concurrent paid offers is post-v0.17.

### Before Part B

4. **`peerSupportsV05` gating.** Mirror `peerSupportsV04`. Confirm: no other v0.5-only feature in scope for v0.17 — paid expert invite is the only thing gated.
5. **Federation-drop during a paid expert session.** v0.16's design choice 5(a) says "immediate eviction" of federated members on fed-drop. For PAID experts mid-session, that's wrong — we'd lose the 30-second grace. Recommendation: `cleanupFederatedMembersForPeer` checks for `r.paidInvitees.has(member.username)` and starts a 30s grace timer for paid members instead of immediate kick.
6. **Cross-server escrow flow — INVERTED from 1:1 paid calls.** v0.17 design: admin's server is treasurer (holds the cap on Hive in admin's-server-escrow, disburses to expert at settlement). Expert's server is router only. **This is the OPPOSITE of the 1:1 paid call pattern** (where callee's server is treasurer). Reason: rug-pull protection — if the cap lived in the expert's escrow, a malicious expert could change their escrow keys mid-session and abscond. Confirm before building Part B.

### Before Part C

7. **Live ticker frequency.** Per-second emit per active room only; emit only to admin + that specific expert (not broadcast to all room members).
8. **Refund receipt UI.** Lobby system message + extend the existing `v4call-ledger.db` schema for paid-expert receipts. Confirm DB-extend vs. separate file.

## Test plan template (apply to each part)

After each Part ships and the user rebuilds:

### Part A — Local paid invite (one server)

1. cnoobz creates `#test`, opens 💎 paid-invite modal, picks reeman (local), sets connect fee 0.001 HBD + 1 HBD/hr + 5 min max. Sends.
2. reeman sees accept-terms modal: "@cnoobz invites you to #test as paid expert. Connect: 0.001 HBD. Rate: 1.000 HBD/hr. Max: 5 min." Accepts.
3. reeman joins #test, has a 💎 badge in user-list and on their video tile.
4. Live tickers: cnoobz sees spend going up (~0.0167 HBD/min); reeman sees earnings going up (after platform fee).
5. After 2 minutes, reeman clicks Leave Room. Settlement: cnoobz's escrow pays connect + 2-min duration. reeman receives net. Platform fee deducted.
6. Try Decline: reeman declines → cnoobz sees `⚠ @reeman declined paid invite to #test`. No payment.
7. Try insufficient escrow balance: cnoobz tries to invite reeman with terms that exceed cnoobz's escrow balance → server rejects with clear error before any popup is sent.
8. Try mid-session disconnect: reeman's browser tab crashes → 30s grace → settlement fires for elapsed time only.
9. Try max duration: invite for 1 minute max, leave it running > 1 minute → settlement caps at 1-minute duration.

### Part B — Federated paid invite

1. cnoobz on v4call.com opens 💎 paid-invite modal, picks `noblemage@hive-book.com`, sets terms. Sends.
2. v4call.com server logs `→ room-invite ... payload: { paidExpert: ... }` to hive-book.com.
3. noblemage on hive-book.com sees accept-terms popup with terms + source-server badge.
4. Accept → noblemage's home server forwards `room-response: accepted` over federation → admin sees "✓ accepted" → noblemage opens temp Socket.io → joins #test with 💎 badge.
5. Live tickers update on both sides; payment is on-chain (cnoobz's HBD → cnoobz's-server-escrow on v4call.com — NOTE: admin's escrow, not expert's, per the inverted flow).
6. Settlement: v4call.com (admin's home server) disburses to noblemage as a cross-server Hive transfer. Refund of unspent cap stays in cnoobz's escrow on v4call.com.
7. Mixed-version test: try inviting from v0.5 → v0.4-only peer → admin gets "peer needs v0.5 for paid invites" error before any wire send.

### Part C — Polish / edge cases

- Live ticker accuracy with multiple paid experts (post-v0.17 expansion — for first build, only one offer at a time per inviter)
- Federation-drop while paid expert in room → grace period before settlement (vs. immediate eviction for free federated members)
- Refund + earnings receipts visible in lobby system messages

## Why v0.17 matters (the seed feature)

v4call up to v0.16 is "callers pay callees for receiving" — cool but competes with WhatsApp + voluntary tipping. v0.17 flips the direction: "I (the room admin) can offer payment to bring an expert into a room I'm working in." Different category entirely. Use case from the user's own framing: when working on a project and you need short bursts of expert help on a language / tool / domain you'll touch for days or weeks then drop, some experts only show up if there's payment or token reward. v4call already supports HBD + custom Hive-Engine tokens (CNOOBS as a worked example), so this slots in naturally.

**Not a marketplace, not a paid-consultancy platform** — just the payment primitive for inviting domain experts to a specific session. Discovery / reviews / trust layers are explicitly out of scope.

The `payload` envelope was designed at v0.16 specifically for this. Get the design right and v0.18+ extensions (split-payer, member-funded, etc.) are all incremental — no further wire-format changes.
