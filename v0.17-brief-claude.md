## Where we are

- **v0.16 is shipped + production-deployed** on call.completenoobs.com ↔ hive-book.com. Cross-server rooms work end-to-end: federated invite handshake (`room-invite` / `room-response`), cross-server join via temp Socket.io, multi-party WebRTC, federated badge in user-list + tile labels, federated token-gating, banlist auto-kick by canonical `user@server` form, federation peer drop → immediate eviction. XSS hygiene pass also shipped (event delegation for dynamic onclicks).
- **Federation protocol at v0.4.** `protocol_version: '0.4'` in the hello envelope gates v0.4-only features. v0.3 peers continue to federate fully for everything they could do at v0.3.
- **The `room-invite` envelope already has the `payload: {}` hook** that v0.17 will populate. No new federation message type needed — paid-expert invites just populate `payload` with the terms (connectFee, ratePerHour, currency, maxDuration).

## Why v0.17 is THE seed feature

v0.16 and earlier compete with WhatsApp + voluntary tipping (caller pays callee for time) — hard sell, low values per interaction.

v0.17 reverses the payment direction: **the room admin pays an invited expert for joining and contributing.** That competes with Clarity.fm / Maven / Intro / Fiverr-Consultations — markets where $50-500/hr is normal, on-chain settlement is a feature (transparent, trustless, instant), Hive's micropayments are competitive vs. Stripe/PayPal fees. **Real wedge.**

3. **CSS variables only.** Dark theme. IBM Plex Mono / Sans.
4. **No comments explaining what code does** — only why-comments when non-obvious.
5. **`.shown` class pattern for hidden-by-default buttons.** Never `style.display = ''`.
6. **Federation backwards-compat is non-negotiable.** v0.4 peers must still federate fully with v0.5 peers for everything they could do at v0.4. v0.5-only features (paid expert invites carrying a non-empty `payload`) gate on a new `protocol_version: '0.5'` hello field — same pattern as v0.4 → v0.3.
7. **The `payload: {}` envelope was designed for this.** The v0.16 `room-invite` envelope is `{ invite_id, from_user, to_user, room_name, source_server, payload }`. v0.17 populates `payload` with `{ paidExpert: { connectFee, ratePerHour, currency, maxDuration, ... } }`. **Do not invent a separate `paid-room-invite` envelope.** The whole point of `payload` was to avoid a wire-format change for this.
8. **Hive `condenser_api.get_discussions_by_*` `limit` cap is 20.** Stated for completeness; not directly relevant here.

## v0.17 — locked-in design (from CLAUDE.md)

These are decisions already made; do not re-litigate:

- **Payer model: admin only.** The room admin pays the expert from their own escrow. Splitting between members deferred.
- **The invite IS the negotiated contract.** Admin sets `connectFee + ratePerHour + currency + maxDuration` in the invite payload. Expert sees explicit terms before accepting — no surprise rates. Accept = consent to those exact terms; expert's normal rates post is ignored. Optional client helper: pre-fill the offer with the expert's posted rates so admin can negotiate from there.
- **Connect fee bundled with final settlement, NOT charged on join.** Expert joining adds connect fee to the running tally; pro-rated duration cost adds to it. Final settlement at session end pays the total. Protects against accidental disconnects: if expert drops by mistake and admin re-invites, admin can choose to waive the connect fee on the second invite.
- **Termination flows — same settlement.** Voluntary leave / kick / room-end / connection-drop all settle the same way: final bill = connect fee + (actual duration × ratePerHour), capped at `maxDuration × ratePerHour`. 30-second grace period for reconnect (mirrors existing 1:1 call disconnect handling) before settling.
- **Same-room model.** Expert joins as a normal participant with a 💎 "paid expert" badge in the user list and on their video tile. Sees and speaks with everyone. Not a sub-room or special bubble.
- **Cross-server escrow flow.** Admin's server is verifier + router (re-verifies on-chain, forwards `payment-verified` over federation). Expert's server is treasurer (holds the expert's escrow key, disburses to expert + takes its platform fee, refunds any unspent cap to admin's server as a Hive transfer). Mirrors the existing 1:1 federated call payment pattern.
- **Expert UI.** Earnings ticker mirroring the existing caller's spend ticker (counts UP instead of down). Clear "✓ Accept terms" / "✗ Decline" modal with the explicit rate breakdown. 💎 badge in their own user-list row + on their video tile.
- **Admin UI.** Offer-builder modal at invite time (currency picker, fee fields, max duration), live-spend ticker per paid invitee while session runs.

## What v0.17 ships — three independent parts

Each part is shippable independently. Test after each part. Do not bundle.

### Part A — Backend + minimal UI: local single-server paid expert invite (1-2 sessions)

**Today:** v4call has free room invites (Part A v0.16) and free room join (Part B v0.16). Paid 1:1 calls already exist (v0.11). v0.17 reuses the calls payment infrastructure for room-scoped paid invites.

**Part A scope:** end-to-end on a single server.
- Admin clicks `💎 Invite paid expert` button in the room (new). Modal opens: select user, currency picker (HBD or any Hive-Engine token from the existing payment-picker code), connect fee field, rate-per-hour field, max duration. "Send paid invite →" button.
- Expert receives a popup with the explicit terms: "@admin invites you to #room as a paid expert. Connect fee: 0.001 HBD. Rate: 1.000 HBD/hr. Max: 60 min. ✓ Accept terms / ✗ Decline".
- Expert accepts → server adds to `r.paidInvitees` Map (which exists as a forward-compat hook from v0.14 — never populated until now). `activePayments[callId]` gets a per-expert entry with the negotiated terms.
- Expert joins room — `joinedVia: 'paid'` (the v0.14 forward-compat branch). 💎 badge in user-list + video tile.
- While in room: server tallies elapsed time × ratePerHour against the admin's escrow. Live ticker on admin and expert sides.
- Settlement on leave / kick / room-end / disconnect-after-grace: admin's escrow pays expert net (after platform fee), platform fee to server, any remaining cap refunds to admin.
- 30-second disconnect grace mirroring existing 1:1 call grace.

**New socket events (single-server scope):**
- `room-paid-invite` (admin → server): `{ room, target_user, terms: { connectFee, ratePerHour, currency, maxDuration } }`. Server validates admin is room creator, target is online, admin has escrow balance ≥ `connectFee + (maxDuration / 60 × ratePerHour)`.
- `room-paid-invite-arrived` (server → expert): same shape as the existing local `room-invite` socket event but with a `terms` field.
- `room-paid-invite-respond` (expert → server): `{ invite_id, response, terms }` — terms echoed back to confirm consent.
- `paid-expert-tick` (server → admin + expert): per-second cost update for live tickers.
- `paid-expert-settled` (server → admin + expert): final receipt with breakdown.

**Server-side state additions:**
- `r.paidInvitees: Map<username, { connectFee, ratePerHour, currency, maxDuration, acceptedAt, callId }>` — already exists as the v0.14 forward-compat hook, now actually populated.
- `activePayments[callId]` — extend to track paid-expert sessions (existing structure already covers caller/callee/escrow/disbursement).
- The join handler's `else if (r.paidInvitees.has(canonicalUser)) joinedVia = 'paid'` line already exists from v0.14 — was a no-op until v0.17. Now it's the path for paid-expert joins.

**Files modified for Part A:** primarily `server.js` (paid-invite flow, settlement logic, ticker emit), `public/index.html` (offer-builder modal, accept-terms modal, 💎 badge in user-list + tile, earnings ticker for expert, spend ticker for admin).

### Part B — Federation: cross-server paid expert invites (1 session)

**Today (after Part A):** local paid expert invites work on a single server. The `room-invite` federation envelope's `payload: {}` is still empty.

**Part B scope:** populate `payload` with the paid-expert terms; cross-server flow.
- v0.16 admin types `@expert@peer.com` into the offer-builder, fills in terms, sends. Server populates `payload: { paidExpert: { connectFee, ratePerHour, currency, maxDuration } }` and sends `room-invite` over federation.
- Expert's home server delivers the popup with the terms. Accept response carries the terms back as a consent receipt.
- Expert opens temp Socket.io to host server (same v0.16 mechanism). Host server validates `payload.paidExpert` matches the `pendingFederatedInvites` entry, populates `r.paidInvitees`, expert joins as `joinedVia: 'paid'`.
- Cross-server escrow: admin pays admin's-server-escrow on Hive (or token). Admin's server verifies, forwards `payment-verified` over federation. Expert's server re-verifies, settles at session end (callee-net to expert, platform fee, refund of unspent cap back to admin via cross-server Hive transfer — same as 1:1 federated call refunds).

**Federation protocol bump to v0.5.** Add `protocol_version: '0.5'` to the hello envelope. v0.4 peers don't understand a non-empty `payload.paidExpert` and shouldn't receive paid invites. Gate via `peerSupportsV05(domain)` helper alongside the existing `peerSupportsV04`. Falls back gracefully (admin gets "peer needs v0.5 for paid invites" error before any wire send).

**No new federation envelopes.** The whole `payload` hook design from v0.16 was for this. We add fields inside `payload`, not new envelope types.

### Part C — Polish + edge cases (1 session, optional)

- Live tickers: per-second updates on admin's and expert's screens. Admin sees per-expert spend if multiple paid experts in the room.
- Disconnect grace: existing 30-second pattern from 1:1 calls extended to paid-expert mid-session disconnects. Federation-drop while paid expert is in room: do NOT immediately evict (override v0.16's design call 5(a) for the paid case). Settle normally if 30s elapses without reconnect; otherwise let them rejoin.
- Refund flow on early termination — admin sees their refund receipt; expert sees their net earnings receipt.
- "Connect fee waived on this re-invite" toggle in the offer-builder (per locked-in design) — covers the accidental-disconnect-and-re-invite case.
- Kick mid-session: admin clicks ban → expert kicked → settlement fires for the time they were in. Same as voluntary leave from a settlement perspective.

## Things to ASK the user about before each part starts

For each part, before generating any code, ask:

### Before Part A

1. **Offer-builder UX surface — where to put it.** Two options: (a) new 💎 button alongside the existing 📌 (spotlight) and 👑 (admin transfer) per-row buttons in the room user-list; clicking on a non-paid user pre-selects them in the offer-builder. (b) standalone 💎 button in the room toolbar opens a modal with a user picker. Recommendation: (a) — fewer modals, more discoverable, mirrors how spotlight/admin-transfer work.

2. **Connect fee billing default.** Locked-in design: bundled with final settlement (NOT charged on join). Confirm this still holds — the alternative would be charging connect fee upfront on accept. Recommendation: stay with locked-in design; adds a "waive on re-invite" toggle later in Part C.

3. **Multiple paid experts in one room.** Allowed? E.g. admin invites two experts simultaneously, pays both. Each ticks against admin's escrow. Recommendation: yes, allowed. `r.paidInvitees` is a Map keyed by username; nothing structural blocks it. Per-expert ticker rows on admin side.

### Before Part B

4. **`peerSupportsV05` gating.** Mirror `peerSupportsV04`. Confirm: no other v0.5-only feature in scope for v0.17 — paid expert invite is the only thing gated.

5. **Federation-drop during a paid expert session — design call.** v0.16's design choice 5(a) says "immediate eviction" of federated members on fed-drop. For PAID experts mid-session, that's wrong — we'd lose the 30-second grace and settlement might fire prematurely. Two options: (a) `cleanupFederatedMembersForPeer` checks for `r.paidInvitees.has(member.username)` and starts a 30s grace timer for paid members instead of immediate kick. (b) immediate kick for everyone, settlement fires immediately with what's accrued. Recommendation: (a) for paid; (b) for free. Conditional behaviour in the helper.

6. **Cross-server platform fee split.** When admin on v4call.com pays expert on hive-book.com, who collects the platform fee? Locked-in design says "expert's server takes its platform fee" — confirm. Or do we want a fee split between source server (verifier) and host server (treasurer)? Recommendation: keep locked-in design (expert's server only) — simpler, matches existing 1:1 federated call flow, easier to reason about.

### Before Part C

7. **Live ticker frequency.** Per-second emit is fine for one room. With many concurrent paid sessions across the federation, server-side tick emit could get noisy. Recommendation: per-second for the active room only; emit only to admin + that specific expert (not broadcast to all room members).

8. **Refund receipt UI.** Admin sees a final summary of what they paid + got refunded. Expert sees their net earnings. Recommendation: lobby system message + add a `paid-expert-receipts.json` ledger file alongside the existing `v4call-ledger.db` for audit (or extend the existing DB schema — confirm preference).

These are real design choices the user should make, not defaults you should pick silently.
